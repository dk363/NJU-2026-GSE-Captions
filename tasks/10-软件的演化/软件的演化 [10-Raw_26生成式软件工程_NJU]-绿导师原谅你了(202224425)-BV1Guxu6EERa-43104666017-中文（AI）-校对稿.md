今天我们继续讲 DeepSeek Harness。上一次讲了 dsh：怎样扩展它，从代码结构上看到的插件设计，event bus 上的设计，以及怎样用许愿的方式接上各种各样的插件。我们今天继续进到 DeepSeek Harness 里面。

但我感觉最近眩晕、瘫坐的频率又变高了。今天早上起来发现：反正 OpenAI 声称它找到了一个去证伪 Exponential Time Hypothesis（指数时间假说，ETH）的算法。本来是说大概是二的 n 次方——对某些 3-SAT 一类问题——那是不可能突破的界限；但它说找到了一个结果。它没有找到多项式算法；如果找到多项式算法，这世界就崩塌了，P 就等于 NP 了。没有。但它把这个界限往下压了一点点，其实颠覆了很多人对这件事的认知，同时还有一些别的非常大的结果。

所以我就有一种感觉：我们在上数学课、上理论计算机课的时候追求一种美——说数学的美。你往后想，可能这种美是一种幻觉。它肯定是美的：它很小，有一个非常小的内核，从这个内核上可以推导出非常有趣的结论。举一个例子，跟 Exponential Time Hypothesis 相关的，就是 P 和 NP 的关系。什么是 P、什么是 NP？大家去回想一下；如果你们以后保研面试，老师可能会问这个问题。N 是什么？N 是 not 吗？N 是 non-deterministic，在一个非确定性的图灵机上。

那很自然的问题是：为什么我们要用 P 来刻画 efficient computable？为什么 polynomial time 是我们认为「有效的计算」，而 NP-complete 就是「难的计算」？中间还有没有别的？为什么要用 P？因为你想，一个 n 的 100 次方没有任何意义：n 等于 10 的时候，你就不可能在现实计算机上、在一个 reasonable 的规模下跑出任何有用的结果。n 平方和 n 的 100 次方在 P 上面是等价的，或者说它们都属于 P——这是因为我们追求一种数学的美。

polynomial time 在设置这个问题定义的时候，使得：你有一个多项式时间算法——比如几重循环——那它是多项式时间的；在这个算法里面你可以调用另外一个程序，相当于允许函数调用；只要那个函数调用也属于 polynomial time，你在里面只能生成一个 polynomial 长的输入，再调用另外一个函数，它再经过 polynomial time——可能是平方、三方、四方——返回的结果依然是 polynomial 的。所以 polynomial time 的好处，或者说大家感受到的这种美感是：我们可以任意、自由地使用已有算法库里的算法，无论使用多少次，只要这东西还是 polynomial time，它在 composition、函数调用的意义上是封闭的；封闭以后也允许我们简化很多数学上的运算，推出很多结论。

但某种程度上，我觉得这是人类为了弥补自己的大脑只能想这么多、只能装下这么多抽象时做的一个 workaround。比如说我们试图去理解「有些问题是不是必须要二的 n 次方才能解决」的时候，其实并不知道算法上有什么样有意思的 trick 可以把复杂度压下去。就像前几年人类解决了一个近似 linear time 的网络流问题——你会觉得这是一个非常 surprising 的结果：本质上任何两个节点在网络里面都是相关的，但我们却可以用近似线性的时间得到结果。所以我们对各种各样数学问题结构的理解其实有很大的缺陷。

如果我们要说理论计算机科学真正想了解的问题：给定一个计算模型，比如说 RAM model——虽然这个 RAM model 和今天的计算机还不一样，我们有 memory hierarchy——我们有一个 CPU，CPU 可能有一个指令集，比如 load/store、加减的指令集，每一次都可以从 RAM 里花一个周期去 load 或 store。我们就问：给定这样一个可以形式化的计算机——我希望你们在离散数学课学完的时候就能写出「这个计算机是什么」的形式化数学定义——问题也是 well-defined 的：在这个计算模型里，如果给你 k steps，允许你运行这台计算机 k 步，你能解决的所有问题是什么？反过来问，这其实是我们真正关心的：人类想知道我们造一台计算机，到底什么问题能做、什么问题不能做。但我们研究算法时用的是 polynomial time，这是一个非常粗犷的近似，很多细节就被抹平了。当你用精细的计算模型时，每一条指令都必须精打细算：数据放在内存的哪一个位置、怎样排布、要不要做压缩，都会对 k 步产生非常大的影响；但对 polynomial time 这种松散的、随便调用别的函数好像不付出代价的计算模型来说，这些是无所谓的。

所以人类很大程度上一直都在解决一些比较干净的问题。你们都知道生物里面有分类：门、纲、目、科、属、种——其实这也是不完全对的。虽然人类花了非常长的时间去构建这样一个物种的 family tree——那个网站建得非常漂亮，代表人类的文明——但从现代生物学的意义上，这样的树状模型其实受到很多挑战。你可以说猫和狗在现实世界中很容易用分类学分开，或者某些植物——我不是这方面的专家——但如果你仔细去看微观的生物，你会发现界限变得非常模糊。我们想定义这两个到底是不是同一个、是不是同一个祖先来的，这个问题甚至都可能不是 tree，而是一个 graph。所以实际世界的结构其实是很差的。

有一种可能性是：我们刚好处在一个非常平坦的区域——这是我们的物理世界，我们处在这物理世界，但刚好处在一个非常平坦的区域；或者在某一个宏观尺度上它变得比较平坦。平坦就使得我们可以压缩。我昨天跟 GPT 聊天，在想一个问题：对称性其实可以推导出能量守恒——物理规律在不同的时空上应该保持一致，只要这一个 first principle 就可以推出总会有一个守恒量，我们现在叫它能量。但如果世界的结构非常差，我们可能只是刚好处在一个有守恒量的区域，于是经验就可以被压缩，压缩就可以产生智能。所以有一种因果关系是：因为我们正好处在这个区域里，所以我们的 scaling law 给我们带来了各种各样的东西。我觉得也很有意思：AI 带着我们想到很多比较夸张的东西。

当然我不展开那个了。我有一个暴论——最近你们如果刷我的小红书，会看到我发了很多暴论，我要解释一下。以前你们上大学，是家庭给你们投资了教育；你们在中学时也是某种投资：疯狂学习、考上大学；大学培养人才，然后企业把你们买走，你们的劳动力是有用的。但现在这个循环变得越来越困难：如果一个 senior 带上 Agent，超过了一个 junior，那么资本家可能就不想再招应届生了——为了面对竞争，他先把自己的优势稳定住，后面再说交给后人的智慧。所以你们毕业时面临的职场压力会非常大：慢慢大家会发现，招一个 Agent 也可以，我为什么要招一个新人花很长时间来培养？

在这个意义上，我知道大家都很焦虑。所以我有一个答案给大家：你们可以用你们的 AI trajectory 去证明自己。从现在开始，你们所有的 AI trajectory 可以做个压缩：把一些不必要的信息——比如 token 的输出——全部去掉；可以把一些图片、生成图片、你觉得有用的 assets 留下来，就得到一个属于你自己的时间轴。这个时间轴上有你干过的所有事情——因为现在你干任何事都问 AI：今天想吃什么、南大和园有没有开什么新店，都可以直接问 AI。比如我上周去了 CNCC，如果要出去走一走，都是让 ChatGPT 帮我找：告诉它我的位置、偏好、想找什么，让它做一个尽可能 comprehensive 的搜索，它就可以给出一些选项。所以这个 trajectory 你是可以看到的。

在这个 AI 轨迹上，首先你看的是 facts：你今天跟 AI 聊物理了、明天跟它聊天文了；你的想法是什么、AI 给你的是什么、你给它的反馈是什么；最终生产的那些代码能不能运行；哪些想法来自你、哪些来自 AI——这些 facts 都是可以审计的。虽然任何方法总有上有政策、下有对策，你总有办法去抵抗它，但这样一份不可变的日志应该更方便用人单位来审查你：它可以随便挑，比如说 2026 年 3 月 10 号你跟 AI 讨论了这么一个东西，你对它还有没有印象？用今天的眼光看，你怎么看那时的对话？你几乎无法造假——只要随机采样：如果你对这件事有记忆、能说出正确的东西，那你几乎肯定是自己做的。就算伪造了这个 trajectory，最后进入面试也会一下子被打回原形。所以这个不可变的记录成为非常好的人物画像，甚至还可以评估你的成长潜力。

比如说你们高考都考一样的分数、同一个省同一张卷子——各科分布或题目分布也可能不一样——但都进到南京大学以后，我们其实想评估的是潜力到底怎么样。起跑线可能都是同样的高考分数，但未来一种是：进大学那一刻就是人生巅峰，从此以后再也没有学进过任何东西；还有一种是：进大学以后能力不断增长，不断在一些地方发现模式——比如在某一个时候发现怎样和 AI 交流更好，把一个 skill 沉淀到你的 harness 里，找到比较好的方法，从此以后在日志上可以推出：你的方法论发生了改变、人生观发生了改变。这些细节都可以在 trajectory 上发现。

某种程度上你愿意的话——你们是学生，不带有商业机密这类东西——可以把学习历程交给用人单位（学习时都是人类已经有过的东西），用人单位就可以全面评估你的能力和潜力。这样的东西就好像没有隐私：你现在觉得把衣服脱了就没有隐私；但在 AI 的时代，如果你有这个 trajectory，它有点像思想钢印的感觉——在窥探你的内心，能够知道你的 potential 在哪里，并且能够准确预知你这个人未来的代数。这是一件非常恐怖的事，仔细想会非常恐怖；但在现在这个时代，对你又是非常 seductive 的一件事：如果你把它保存下来，并且用合适的方式投影成一个简历，至少短期内你会得到回报。相当于你跟魔鬼有一个契约，出卖了自己的灵魂——如果我把所有跟 ChatGPT 的 trajectory 全部拿出来，我就有一种把灵魂都出卖给魔鬼的感觉，因为某种程度上 OpenAI 会对我了如指掌：我在这个世界上的位置在哪里，它真的是了如指掌，因为我把所有生活都交给它了。

你再往后想：以后我们也不需要再通过见面、再聊天的方式来交朋友了。我经常有这样的体验：有些同学过来找我聊天，聊聊对 AI 的看法、对 Agent OS 的看法，聊着聊着开始收敛，最后达到「英雄所见略同」的状态——原来你也是这样想的，我们就在这件事情上达成一致，可能有些分歧最后也达成一致。但以后当你有这个 trajectory，也不需要跟别人花很长的时间来辩论了：你们只要派出你们的 Agent 先聊一聊，就立即知道观点一致的部分在哪里、不一致的部分在哪里，然后继续展开辩论，辩论完了再由 Agent 来增强。我现在发现：想任何问题的时候，AI Agent 都代表了这个领域里面所有的知识。所以我会有一个想法，可能比较粗糙，但 AI 可以帮我补全无数细节，甚至告诉我哪些部分别人想过、那论文是什么，哪些地方我想得不够周到，哪些地方可能大家还没有想过。所以人类扩充知识的速度会变得非常非常快——然后也不知道什么时候，突然有一天就全人类都被「斩杀」了。

那就另说。但我觉得它带来一些好的 side effect：比如说有可能成为这种颠覆性的产品——可以用来匹配交友。你的 personality、你的人格都已经被编码在你的 AI trajectory 里的时候，你也不需要别的了——开个玩笑——只需要由 OpenAI 来给你分配对象就可以了。我觉得这是一个非常恐怖的世界；但至少对我来说，我又有一种无法抵御的倾向，想把自己交给这样的 AI，因为我会在这个过程中获得优势：AI 一方面在窥探我的内心，另一方面又在不断给我正向的反馈，不断强化我，可能使我在竞争里面获得一定的优势。我觉得这是一个值得大家思考的问题；也作为给大家上课时的一个小小 reward：你们至少可以这样去「保持隐私」——你只和 OpenAI share 你的秘密，或只和 DeepSeek share 你的秘密；最终你可能需要一个好的 skill，把 trajectory 蒸馏成一个简历或一个网站，那个网站眼前一亮，用人单位就会给你一个非常好的 offer。当然，一旦大家都想到要做这件事，这件事就会烂大街，又会进入恶性内卷，你们又会 reward hack 这个过程；但如果你们作为世界上第一批意识到这件事的人，就可以少 reward hack 一点——竞争者还没有涌入，你提前做了这件事，就可以更多地追寻自己的内心。

以后真的有可能：我觉得上学本身就是一种期货投资——你现在把青春都给大学了，毕业以后如果再找不到一份好工作，落差就非常大。但以后真的有可能会「贷款上班」：你要上班，就先承诺你可以超过 AI，先交保证金；如果在一段时间里、在 mentor 带领下，你超过了 AI、给公司带来了价值，就可以得到回报；但如果你最终评价是一直不再成长了，那保证金可能就不退给你了——是真的有可能会发生。所以我觉得我们也许会走向一种类似于核不扩散条约一样的、AI 能力不能再增长的东西——Anthropic 和 OpenAI 就在讨论这件事，但好像没有变得更缓和的趋势。一些有意思的思考。

好，我们回到 DeepSeek Harness。刚才是一些我今天因为看到新闻以后临时加上的内容，跟大家分享一下。

我们说 dsh 是一个操作系统对吧。它说 everything is a plugin，意味着内核其实不带任何实际的功能，就像操作系统。操作系统是什么？它是 process 进程的 API：创建进程——spawn 或者 fork；然后可以有处理操作系统里面对象的指针——handle 或者文件描述符；你通过文件描述符可以 read/write 文件内容，可以管理 persistent 的数据。那 DeepSeek Harness 当然有点像这样的操作系统：它什么也没有，但有一个 event bus，以及它的原生插件——规定了比如说你怎样和 Agent 交互（agent.inject），怎样和模型的上下文交互，等等。

当然这个「航母」很有意思：航母已经造好了，但我觉得它上面的飞机还处于试验阶段——它还不知道这航母上能放什么武器；现在有一些试验飞机，还没有一种类似于今天航母战斗群的概念。所以我首先愿意期待一下：这样的生态可以怎样长大。也许最终成功的未必是 dsh，但围绕 Agent 产生的生态会让你们每个人使用起来更方便。因为好像 dsh 要发移动端的应用了：如果你的 PC 可以长期开机，移动端可以和 PC 建立通道，PC 就可以一直在后台工作——就像 Grok Bot 那样，只不过你用你自己的 PC。我觉得这在中国是一个非常好的模式，它一定是我们的未来。

比如说，你们回去可以在 DeepSeek Harness 上许愿做一个：你的 Agent trajectory、你的人物画像。因为 dsh everything is a plugin，你可以很容易地监听到各个插件的行为、你和插件的交互、以及插件和上下文的交互；包括你可以把模型的上下文字口令给 persist 下来，然后做一个投影——比如做一个功能叫「实时简历」：每天简历都在更新，但你自己不需要维护它；一个属于你的画像的简历，可能有一个非常 fancy 的界面。比如说你们都知道 GitHub：点一个人，可以看到他的贡献墙——有一个时间轴，里面一块一块的，颜色越深代表今天如果提交了五次就是深绿，提交两次就是浅绿，今天摸鱼什么也没干就是空白。当然这个也可以作假：你看 Agent 来提交，所以我现在这面墙非常绿，因为这些提交都是 AI 帮我做的。你可以把简历实时投射成这样的东西。

插件的生态就像操作系统一样。UNIX 在诞生的那一刻起做梦都不会想到：今天我们有可能会写出 `cat ... | Claude` 这样的用法；但这样的用法一直都在演进当中——可能以前是 too long don't read，管道给一个 pager，就可以查看这样的手册。很有意思的生态未来。所以 dsh 未必是最后活到最后的产品——可能是某个商业公司的产品活到最后——但构建「航母」生态肯定是未来。所以我今天要讲一个航母的故事。

这个故事很有意思。你们都知道造航母很难。中国的第一艘航母严格来说也不能说百分百由中国制造：买了一个苏联的航母，再做改装。我是什么时候意识到这件事的？2019 年我去了一趟 San Diego，那里有一个博物馆。同一个位置我有一张照片——就是从这个位置去看这艘航母：USS Midway，中途岛号。它是 1945 年下水的，下水的时候二战好像已经结束了，日本已经投降，所以它不需要再去太平洋战场上打日本人了；但后来这艘航母服役了非常长的时间，1970 年代经历了一次现代化改造，然后应该是 1992 年海湾战争的旗舰。

我当时到这艘航母里，第一个感觉就是非常震撼：这样的一个复杂系统——因为我是做软件的——我不知道是如何能够构建出来的。这是航母内部的一些老照片，大概就是 1945 年下水时的状态。你可以看到航母是一个非常复杂的系统：里面的管线，比如说要走蒸汽——不像现在大部分都是电器，只要有电就可以驱动一切，只要有电线就可以了；那个时候还有蒸汽，通信线路也要有电。更重要的是它还要做损管：航母是一个战争机器，随时都可能受到鱼雷、轰炸机的袭击。

当时航母上的志愿者其实是在当时航母上服役的老兵。我就很好奇，问他说：这样的一个系统——他肯定不知道系统是怎么构建出来的——但出现了故障要怎样维护？那个老兵亲口告诉我：这些航母的设计都是那些非常天才的人做的，他们完全不需要知道这是怎么做的，但每一个人都会得到一本操作手册；手册上明确写了：你遇到什么样的情况应该干什么——就跟现在飞机一样，如果你们玩过一点模拟飞行，都有非常长的操作手册：什么时候做什么，发现什么情况做什么；比如说发现什么地方起火了，就要把几号阀门从什么状态改成什么状态。你就看到设计者其实推演过了各种各样的可能性，使得这样的航母能够真正在战争当中起作用。那时候我也理解为什么中国看起来有那么多船，为什么造航母显得那么困难——它是一个战争机器。

但真正让我觉得最有启发的，其实是 2019 年在那艘航母甲板的底层：最底层有一个陈列柜，放了从最早的美国海军第一艘航母到当时最先进的航母，一代一代是怎么演化过来的。这个故事给了我一点启发：其实所有的航母都不是第一天马上造出来的；如果你把它的历史追溯到最原初的那一个点，那个点可能非常简单，然后在那个点上演化、演化过来。所以今天我讲的其实是软件演化的故事——我们当然也会看 DeepSeek Harness 的演化。那我们先看一下航母是怎么演化的。

这是 1945 年的 USS Midway。如果你往历史往前推：古代文明其实都有桨船和帆船；在长期几千年的演化里，人类终于可以造出有足够好的材料、有足够多的经验——他们发现如果把船造成这个样子，就可以在海上做长途航行。Santa María 原来是一艘商船，1492 年成为哥伦布首次发现新大陆的旗舰。大家觉得还是可以理解的：上面都是机械装置，某种程度上是人类可以驾驭得了的复杂性。

然后到更后面：你们有没有看过《泰坦尼克号》那个电影？我们有代沟哈——那是我们那个时代最火热的电影之一。在 Titanic 之前，比如说 1811 年的 New Orleans（新奥尔良号），在密西西比河沿着 Ohio River，1812 年抵达新奥尔良。那个时候的汽船是高压蒸汽的汽船；你看到「轮船」为什么叫轮船——因为轮子是在外面的，不是今天螺旋桨还在水里看不到的地方。你会发现世界上所有这些东西都是平滑演进的。这有点像人类的一个局限：我们说 everything is the same machine——我们总是从一个 initial state，不管是 repo 还是别的；人类受到大脑的限制和物理世界做实验的限制，任何时候都只能往前做一个小的 delta：可能发现某一个结构有用就加上去，发现某一个结构没有用就减下去。有可能在某一个时间段——比如说在古代——桨和帆一直都是并存的，既有桨也有帆；后来到要远航的船时才发现桨已经没有用了，桨就被收掉了。也可能有一个时期，明轮船轮和螺旋桨舵是同时并存的，终于有一天大家发现其实不需要这样的轮子了，只要螺旋桨就够了，所以就消失了。所以不管是航母的演化历史还是别的历史，人类就是平滑一点一点把一个大的东西给造出来的。

汽船会变得越来越好，因为它可以挣钱；可以挣钱以后大家会去研究更好的汽船。那是 1811 年——你看我们从 1492 年到 1811 年，再到 1913 年。然后这是我觉得我那天收获最大的一张图：它讲了 USS Langley——美国海军的第一艘航空母舰、试验型的航空母舰。这艘航空母舰并不是一艘真正意义上我们现在这种航空母舰，而是直接从一个运煤船改来的。所以航母并不是一天造成的：运煤船——如果你看运煤船，想想泰坦尼克号，运煤船跟泰坦尼克号就很像；再看泰坦尼克号和这种蒸汽船，烟囱在这里——又是平滑演进的；再往前，可能也是平滑的，一点一点。

然后他有一个很天才的想法，又是一个非常小的 delta：我们有没有可能把这个运煤船——反正运煤船能够载重——上层运煤的部分换掉，换成一个木质的甲板，这不就变成一个跑道了吗？相当于一句话：我能不能把机场搬到运煤船上？就这一句话。接下来就是推理——工程师模型的推理——然后做实验：它会计算跑道多大才够，以及飞机放在哪。如果是机场，可以在边上修一个厂房；但在船上肯定不行，肯定应该放在中间——船上空间有限，要尽可能利用——所以甲板应该放在上面，把机库放在下面。那时候你就需要一个电梯。电梯一般是在航母甲板的某一个位置上；现在的现代航母一般是在侧面，或者有多台电梯；但那个时候就是在甲板的尾后端有一部电梯，可以把飞机向上下运输，运上去以后飞机就可以起飞。其实一直到二战的时候，航母飞机的起飞速度都是一个很大的瓶颈：需要把飞机从中间的机库运到甲板上才能起飞，但它没有很大的并行的「算力」。

这是一些比较有意思的老图：USS Langley 的升降机，把上下层连接起来。所以这是一个实验性的想法：可以把机场放到船上。等到第二次世界大战的时候，日本人和美国人在太平洋战场上证明了航母的用处。这里你也可以看到电梯——这里应该还有，侧面应该还有一部电梯。这个应该是使用了钢甲板的航母。

于是在演化过程当中，不仅有这样比较大的、比较 significant 的架构改变——他重构了，加上了一个很大的 feature，一种之前所有的船都没有的 feature，把它改造成了一个机场——也有很多小小的改动，比如说管线的设计。

甚至一些非常细小的：两个管路谁应该在左边、谁应该在右边，都有可能会对船的可靠性产生影响。比如说有一个管路通的是高热蒸汽，如果保温做不好，可能会影响到什么东西。所以当第一版设计时发现可能没考虑到这一点，第二版就把它做了。不仅有这样的架构改变，还有这种比较小的——比如 bug fix——以及一些子系统的重构。

所以看起来我讲了一个航母的故事，其实我讲的是：任何系统在设计时都会经历的这样一个通用过程。当然了，其实我们也在造航母了——这个链接是我在造航母的链接——我们也要造一个像 DeepSeek 那样的东西。好，不能打太多广告，因为这只是上课时间。我们现在也想造一个像 DeepSeek Harness 一样的东西；大概处在这个阶段：我们已经造出来一条可以起降飞机的「航母」了，但它还有很多问题。

因为在 AI 时代，造航母的方式变了。以前你看我们要造航母，人类几千年得从最早的独木舟开始：一块木头挖一块，人在上面它就是个船；然后发明了桨、帆、舵，发明了各种各样的东西。但今天我们有了一个能力近乎无限的 chain of thought 的模型，所以可以从一个起点开始直接大跨步往后跳：我不需要把完整的东西都做出来，可以做一个 MVP；在 MVP 原型试验成功以后，可以随时再说——不要紧，我们再回到这个点重新构造。这是 AI 时代的软件开发：许愿式编程——我可以直接许一个愿，先看它造出一个什么东西来，然后再一点一点沿用比较严格的过程，把每一个东西都做好。所以其实我们也在造航母了。我们承诺是一个和 DeepSeek Harness 一样好的操作系统——一个真正的操作系统，同样可以支撑一个生态。如果你们有兴趣，可以读一下我公众号的征友帖，来找我聊一聊——属于夹带私货了，开玩笑的。

所以我讲了一个软件的故事。我觉得那天在 USS Midway 上面的收获，可以说是那些年都没有体会过的那种突然顿悟的时刻。我觉得每一个人都是这样的——又回到 everything is the same machine：你是随着时间轴成长的人；在这个时间轴上，你可能一开始并没有展现出什么，但突然有一天你就领悟了某一件事情，就不断在提高。我相信你们每一个同学在人生中都经历过这样的顿悟时刻；你可能会把它记下来，写一篇日记——也许这个记忆就尘封了，再经过三年或五年就想不起来那一刻；但如果你有一天突然回想起来，又重新想到那个时候的启发，就是不断在积累知识当中进步。所以你看：人也是这样，软件也是这样，任何一个复杂的东西都是这样。

软件和这些都一样：早期通常就是一个非常简单的 idea——哦，我看到一块木头，能不能挖掉一块，我就能从河这边到那边了呢？一句话的解释，那我们就可以试一试，你就发明了船，继续往后发明。一般来说，成功的、或我们印象中成功的软件，通常都是解决了一个真正的问题——可能是一个很简单的 idea：Linux 说我就是想克隆一个 UNIX，免费的 UNIX 供大家用——然后功能就是 UNIX 的功能，一个简单的想法。一直往后走，如果这个想法走在正确的道路上，确实能解决真实世界里的问题，那你就能一点一点通过刚才那种往后改造的方式成功。

早期的时候，比如说 AI 有一个问题：刚才我说它会往后跳步，一下可以跳很远，它也会给你设计一些架构；但这些架构可能随着软件维护——每次要修改——变得越来越难维护。随着 essential complexity 的增加，一开始那个架构可能就是错的——你们跟 AI 编程时应该经常有这样的体验。在人类历史上，其实很多架构经受住了时间的考验；甚至在经受住时间考验的同时，也有很多部分被重构了——就像航母从轮船（真的有轮子的轮船）到今天我们还是说「轮船」，但它没有轮子了。

软件的时间维度：你们过来上大学学 computer science，为什么要上基础课？很大的原因是你们要去学习一些软件系统早期那些设计，以及它怎么随着时间去演化。我觉得调度器的例子并不是一个很好的例子，Python 的例子也不是一个很好的例子——所以你看 AI 还是没有办法共情：当我想谈谈演化、说软件要演化的时候，航母那个例子显然是更好的例子；Kubernetes 可能也不是一个非常好的例子。但不管怎么样——比如说你们入学的时候就没有见过 Python 2、没有用过 Python 2.7，我是从 Python 2.7 的时代过来的——Python 2 和 Python 3 其实不兼容。其中有一个很有意思的语法：Python 2 的 `print` 是空格，`print` 是一个内建的语法——最开始的时候就是说「我就这么随便一做吧」——然后 `print` 空格其实给 AST parsing 还是带来一些小麻烦的：`print 1`。到了 Python 3，`print` 就必须是函数，它不再是一个有点像 keyword 性质的东西。但你可以看到：Python 2 就是因为我们在第一天设计一个最小的软件系统、要做一个人类好用的编程语言时，设计师想 `print` 一定要好用——因为在他设计那个软件最早的时候，几乎除了 `print` 现在没有别的功能——他不会想到今天整个人工智能的生态都安在这个 Python 上面。所以如果你们在学习过程中跟了一个软件的发展，你就能体会到：这个世界其实一直都在做同样的事情。

举一个例子：我们一直都在用简化的版本去理解软件。Linux 0.11 真的很简单——你们到现在都能看到网上可能有一些教程。虽然你们现在学操作系统应该从 xv6 开始学起，这个 0.11 真的什么也没有，没有任何所谓的 advanced technology。你们今天学很多课程时会讲今天什么东西怎么牛——实际上所有牛的东西，就说航母：我是什么时候开始不怕这种比较现代、比较困难的东西的？隐隐约约我们就知道：如果今天的航母很复杂、很厉害，中间一定有一个平滑演进的过程。所以如果你觉得这个很厉害的东西你不知道它是怎么做出来的，就回到一个不存在这个东西的版本——回到独木舟——然后再看一点它的发展历史是怎么把这东西加进来的，你就马上知道了。某种程度上我觉得现在这种「定义、定理、证明」的学数学方式有点反人类：直接告诉你这个东西你自己去悟吧，而没有告诉你其实人类走了多少弯路、都失败了，然后最后才发现这是正确的路线。所以如果你真的倒回去看，比如说 0.11，它就很简单，你就直接看懂了：所谓的系统调用嘛——`read` 好，进来，`read` 就像一个函数调用一样调用进来，执行 A、B、C 三个操作再回去——像 xv6。

我大概是在 Linux 2.6 的时候进入这个世界的；到今天 Linux 已经是一个非常复杂的、人类已经也理解不了的东西。但我去理解的时候，很多时候还是回到最原始的 Linux 2.6：如果在 Linux 2.6 里面我要做这件事我会怎么做？这么做又好在哪里、不好在哪里？那我今天应该怎么做？甚至绝大部分的问题都可以回到比如说 Linux 0.11 的模型上面：如果我要做一个系统调用、要问操作系统要一些信息，我是不是一定要穿过操作系统的边界？有没有可能——这是我上课时会讲的一个例子——操作系统就直接给一个页面的数据，把操作系统的页面和应用程序直接映射共享，让操作系统也可以访问这个页面，让应用程序也能访问这个页面——当然可能应用程序最好不要写它。什么信息可以呢？只要在我的进程地址空间里面放一页：比如说我的 CPU 的 id、比如说现在的当前时间（每秒）；操作系统只要每秒钟写一次这个秒；每次比如说当这个进程创建、或者切换 CPU 的时候，把当前进程所在的 CPU 的 ID 或一些信息放在这——那这个页面就可以共享给用户进程。我可以在 Linux 0.11 里面就把这件事情想清楚，然后再去把这个 feature 加上去。

就有点像我们要做 Git、要版本管理：我们是怎么理解一个复杂的软件系统呢？如果你直接在今天的软件系统上看一个 feature 看不懂，不要紧——你就想：我有没有可能在最早的、或某一个你能理解的版本上把这个 feature 加上？然后你做什么？做一个 git rebase：不停地把这个 feature、这个提交往后挪、往后挪。所以你会知道：在这个历史的演化过程上，如果我加上了一个什么调度算法，对这个 feature 有没有影响？如果没有影响就过去了。你会发现在这个发展历史中，大部分引入的东西跟这个 feature 都是没有影响的——因为如果所有东西都搅在一起，软件是不可能维护的；软件架构设计得好，一定把复杂性分解下去了；essential complexity 有交互有，但如果你新加一个 feature，它可能跟软件绝大部分部分的耦合都相对松。所以你只需要知道：在几个关键的提交上，你的 feature 和谁打架了——你就知道不能用最简单理想的模型去理解这个软件，而是要理解他们怎么打架的、冲突是怎么解决的。就跟我们说数学：人类走了几百年的弯路，最终发现某两个东西应该连在一起用，就把很多东西发明了——group theory 这种东西。

这解释了为什么我们在 pre-LLM 时代都说程序员有三大浪漫——应该是这三个：一定要自己做一个操作系统、一定要做一个编译器、一定要做一个数据库；当然也可能是做一个 CPU。然后今天这个答案变了：你们看到所有投 AI infra 简历的同学都说——我在什么 nano-gpt、nano-vllm 上面改了一个什么东西，做了什么，比如说迁移到多卡上；或者哪怕就是说：我有几个树莓派，或一个什么 RK3588 这种带 NPU、带加速器的小卡，我有四个卡，把它做了一个并行的推理加速，接入了一个我魔改过的 nano-vllm——这些事情都是有意义的，你们都去做。但你们可能没有意识到：我今天把造航母和你们学习都用一个 Git 的 model 来解释了。

所以我觉得这其实是人类的局限。我一开始说震惊瘫坐：人类只能理解简单的东西；而演化其实是人类去把一个东西——如果航母就在这、软件就在这、DeepSeek Harness 就在当前的状态——你去看吧，没有人能够、尤其是新入局的新手，你会感到无尽的复杂性；但你可以通过理解它的发展历史，然后去 rebase 你想要了解的 feature，来理解任何东西。有意思啊。

所以很自然，软件的演化就成了大家研究的对象。我们有好多的——Git history 就是一个宝藏：在有了计算机以后，我们才可以把人类创造一个东西的过程从一开始、从初始状态完整地记录下来——虽然这个过程从人类很早的时候就一直有。所以我其实觉得：今天 AI 时代，我们作为还能守住人类最后一点创新创造力的人类，真的应该去干一些更大的事情——比如说有没有可能把数学发展历史的 Git 给构建出来？我不知道 OpenAI 或者 Anthropic 有没有在干类似的事情；有没有可能把造航母、造船的历史脉络给构建出来？或者说有没有可能把人类的知识历史用一个像 Git 一样——虽然这个比喻不恰当——但我们能把这种分支之间的 rebase 关系也整理出来？

OK，因为我这是软件工程课：虽然你可以透过软件工程去看到任何的工程，我们还是讲软件工程。所以今天我讲那么多，其实带来了一个推论：所有这些东西都是由一个一个小的——不管它是不是线性的历史——都是由一个一个提交组成的；每一个提交都是一个小任务。这是一个非常关键的基本假设。然后这是一个小任务，就意味着绝大部分的提交都是一些比如说像 bug fix、或一个小的 feature request 这样的小任务。那小任务很自然就有一个问题：我们 AI 能不能完成呢？

SWE-bench 是整个系列当中知名度最高的工作之一；然后它也有各种，比如说 Pro，现在还有更长的比如说 Terminal-Bench 这样的基准测试。这些基准测试衡量了我们的模型在软件工程这种 GitHub issue 的任务上表现有多好。虽然我觉得这些论文的作者可能都没有看到——我不知道他有没有看到——也可能看到了：这样一篇 SWE-bench 这样的工作在这个历史上的地位，就是问：大模型能不能把一件小事给做好？当然在那个时候这个答案肯定是不能的。如果我们把它翻到——很有意思，这应该是 2023 年的 paper，那个时候应该是 GPT-4 的时代。你看他还是这样的：模型的输入还不是 workflow，那时候没有 agent 能真正跑得起来——虽然那时候已经有一些 agent 的想法，说能不能逃门——那是因为 GPT-4 的能力其实还是非常强的，但它幻觉也很严重。model input 是要干什么、issue 是什么，然后有一个 golden patch，还有一个……以及有一系列测试用例。这个测试用例也不能说完美吧——因为我们其实仔细研究过 SWE-bench，这绝对不是一个完美的 benchmark。然后很多这种任务，比如说去 fix 一个 bug，其实这个 bug 的引入是因为这个代码在源头上设计出了一些小问题，以至于不停地要修修修修修。如果我作为一个人类的话，我更倾向于是 refactor 那个代码，而不是 fix 这个 bug。但是不管怎么样，这是一个明确的任务，有明确的反馈信号，可以评估你这件事情做对没有。所以它能够用来评估大模型做一件小事的能力。

小事的能力是这样的——很有意思。让我们看一看历史：Table 5 在这里。Claude 2、Claude 3 Opus 在那个时候都是「透明」的模型对吧——虽然 Claude 那个时候声称它在某些表现上……那时候因为 OpenAI、GPT 是如日中天的时候，没有人能打得过 OpenAI；Claude 只能说：哎，我们在某些小领域、专业领域、垂直领域上面比 OpenAI 要做得好一些。然后看到这个惨不忍睹的比例对吧——Claude 3 Opus 3.7% 的 resolve rate。那这个结论就是：完全不行。

而这个方向我觉得它最具有 vision 的地方其实不是说——因为我知道你们有可能有在听课的同学在课题组当中去做 benchmark、做 benchmark 研究，每年你也会看到浩如烟海的 benchmark paper——但实际上这个 benchmark 真正背后的意义在于：我们作为后人，站在人类的高度上，他这个 benchmark「做这件小事」的价值有多大。如果你在软件演化或工程演化的意义上，把小事能够做得非常好，也就意味着你已经把这个演化路线里面绝大部分的东西都跑通了——因为绝大部分这种任务都是小事。它从 GitHub 上面某种意义上 random sample 这种：绝大部分都是——哦我有个 issue 来了，今天程序 crash，你能不能帮我修了；哎呀这个日期本来是以这个格式来写的，我发现日期计算可能不是很精确，比如说没有算闰秒、没有算什么东西；或者说我最好再加一个星期，能不能把这个功能做一个小的改进。你们日常做开发绝大部分时候都是在干这件事。所以 SWE-bench 很好的代表了这种小工作：它告诉我们，如果有一天 SWE-bench 被解决，就意味着工程里面绝大部分 todos 的事情都被解决了。人类就说初级工程师——SWE-bench 其实隐含了一句话说：如果我的 SWE-bench 刷完，低级工程师就被斩杀了，低级工种就全部被斩杀了。所以它预见了今天我们大家都非常焦虑的情况。

而且我们还可以问：软件工程的流程里，什么东西是 SWE-bench 里面没有覆盖的？我们的 initial state——我们在 initial commit 的时候都会有一个计划：比如说我们的 initial state，我们要造航母了，脑袋里面有一个想法，想要造一个这样的航母；当我做出这个决定以后，就会建一个 repo，放一个 initial state、放一个计划——这件事情是不好 benchmark 的。以及当软件到某一个程度的时候——SWE-bench 里面有这种我们见到的：他那个代码写的就像是 slop，非常非常复杂的逻辑；其实是因为在设计的时候有两个模块没有解开，使得我在写那个代码的时候必须要带着那两个模块的状态，代码就写得非常恶心。我们当然为了评价我们的方案，做的办法是把那个整个模块一起重构了；甚至我们重构完以后，那个 bug 就消失了，根本就不会存在那个 issue，根本就不需要被 fix。OK。

那这些小事都被解决以后，还有——就像我刚才说的——终于有一天你小事做得太多、这种琐碎的 bug fix 太多，你受不了了，你开始重构。重构就意味着你有一个架构上的变化，它可能是局部的架构变化。我们说代码总体总设计有个架构，那个架构可能很难改——因为架构改了以后，就有点像 Cloudflare 一段时间以前把那东西从 Zig 全部迁移到 Rust，是一个非常疯狂的事情，竟然没有出笑话。当时我的感觉是：这可以吗？这不会留下两个非常糟糕的 bug 吧？没有——当然也跟那个项目的结构有关系；你如果去迁一个什么 MySQL 这种，我估计就不行了。我们有这种顶层的架构设计，也有每一个代码里面的架构，甚至是你自己代码里面一个函数里面，你到底是写成这种 functional 的 code 还是写成这种 imperative 的 code——这也是一个微架构。然后你任何一个相对来说比较大、到 subsystem 级别的架构改变：它什么时候发生、应该什么时候发生、到底应该什么样算好——这些就非常稀疏。首先在人类的世界里面这样的任务也不多，也是非常稀疏的；非常稀疏就意味着模型没有办法通过大量的这种反馈和信号或样本来学到。但人类是一个非常好的 few-shot learner。人类的能力——我不知道现在大家都希望模型能有这样的能力，也可能是下面一个研究的真正热点：模型到底有没有可能用非常少的样本来泛化。如果能——就就像我在 San Diego 的时候，看到那个航母，想到了一件完全不相关的事情，展开了非常长的思维链，刷新了我的认知——有没有一种可能：模型看到一个案例或几个案例，就开始重构它自己的权重——不要把它当成是 GRPO 里面那种：我本来做这件事情要这样做，我发现这样做 A……比如说这道数学题用三角函数好还是用列方程好还是用数形结合好，去预测 next token、下一句话我应该说什么会比较好——而是他可以根据一个案例去重构它整个模型，三观尽毁的那种感觉，去学到一两个案例里面真正表达的：比如说为什么这个软件一开始在什么时候能够想到要做这件事而且做对了？Linux 为什么在那个时候做这件事情做对了、成功了？为什么在 4.0 的时候要重构、在 3.3、3.4 左右的时候要重构 USB subsystem——为什么整个 USB subsystem 大家都觉得维护不下去了？刚开始的时候是「这个不重要」，就这几种设备不行，要全部重构。这些架构上的变化。

所以我们现在其实需要一个足够好的 taste-bench 了。因为在人类历史上——我今天讲的演化的历史，是任何东西的演化历史：数学、造船、造航母，还是一个软件系统——它的演化都是由大部分是由小事构成的，小部分是由大事构成的。小事解决了，到今天——那我们是不是可以有一个从 Yes/No 或打一个分数，到一个多维度的相对比较？因为如果你要做这个 taste-bench，它和 SWE-bench 不一样：SWE-bench 刚才我们看到他就是测试用例——当然这个测试用例模型不能看到；虽然现代模型如果你要刷分的话都会偷偷泄露一些、以间接的方式泄露一些信息到训练好的模型，这样他就可以在做这个任务的时候表现得更好一点，你又看不出来——因为它不是直接把测试用例泄露进去，而是把一些方法……你看到这种 SWE-bench 型的时候你要疯狂多自己写测试，有一种倾向，他就可以把这个分数调得高一点。但是一件小事他就是要么做完了要么没做完；重构好要么对了要么错了——以这个为奖励。但到大事的时候，我们对于强化学习的反馈就已经很稀疏了。而且其实如果我们回过头看，并不是 Linux 在当时做一个那样的 Linux 可能就是最好的——后面还有更多的经验；以及在重构的时候我可能有多个可能的架构：要不要用 event sourcing，干脆把底层架构也换了？还是要不要在数据库里面加一层缓存，还是用别的方法来解决这个性能问题、用 scale 的方式来解决性能问题？我们其实面临了很多的选择，而每一个选择都不是严格的谁比谁好。虽然最终我们可以说最后像考卷一样——像你们的高考试卷一样，给你们几张试卷，每张试卷有一个总分，总分加起来作为你的总分——但其实这里很微妙：不同的科目代表了你不同类型的能力，甚至不同的题目都代表你不同类型的能力；你的能力、你的画像是一个 vector。有没有一种 human vector，就能准确知道你——根据你那 AI trajectory 得到你真实的画像？它并不不是说你加起来最好的那一个就是——可能最适合这个项目。尤其是对于真实的项目来说，我们需要的是 trade-off：有些东西是不可调和的。比如说你的架构大改了、改成 event sourcing 了，你的重构代价就变大了，引入的风险也增加了；如果你要降低风险，那架构上的代码改动应该要平和一点，但你的工期就拉长了，你可能从这次重构就到达不了你想要的目标。当你面临十几个目标要权衡的时候，其实没有一个绝对的好和坏——这也是现在为什么 AI 做这件事情还做不好的原因。所以我觉得我们需要一个足够好的 taste-bench。像数学已经解数学这种——我觉得可能已经不是小事了，它已经涌现出了我们无法理解的能力；那也许有一天再有下一个 benchmark 的时候，我们就可以见证人类的这个「末日」。我觉得挺有意思的。这是软件的时间维度。

好。所以我上节课说 DeepSeek 还是太慷慨了——DeepSeek 给大家看过的对吧：2026 年 6 月 10 日的第一个提交，它给我们展示了这个航母整个构建的过程。所以你们马上就好奇：比如说今天老师用造航母的比喻讲了软件系统是如何从一开始演化的——我可以给它一些更多的信息。比如说我现在还没有 summary，所以你们不能……我还得打几个字：你们今天可以直接把我 wiki 上面的 lecture notes 贴进去，说老师是这个观点——简化的核心观点是：航母很复杂，但如果从人类的历史上看，每一个演化的决策从帆船到汽船到第一艘航母都是非常连贯的；大部分是 minor 小改动，有些是比较重大的涉及决策变更。所以照着这个思路：重大的设计变更和机制引入——你甚至可以把它当成一个模型的考题，这就是一个 benchmark——某种意义上的。你在长期和 Agent 这样交互的过程当中就知道：哦，应该是什么样的，他应该要思考比较长的时间。

不过没关系，我还是给大家准备了一些。比如说我拿到 DeepSeek Harness 以后干的第一件事就是整理它的提交。这里有一个它最早的 1000 个提交：初始化——就相当于航母，当他真正决定造航母的时候，就有一个 initial state；然后刚开始做一个 minimal viable product，做一个 MVP——一个微内核和需求和架构的场景。你看他在第四个提交的时候以源码形式 vendoring Cordis 的框架包。所以其实很有意思：DeepSeek Harness 在它的 init 之前，Cordis 已经存在了好几年了。Cordis 其实是一个个人的项目——那个老哥就是想要管理他的一些 QQ 插件、管理 QQ bot 的插件；然后他发现这个插件每次要加载卸载就很麻烦，所以干脆做一个架构吧。所以这其实你看他也经历了一个过程：一开始管理一些插件，也是自己手工管理、没有任何章法的管理；然后突然有一天他发现——我有一个方法，或者他发现了一个东西——那这个发现就很重要。所以可能这原始的几个架构上的设计的 commit 就成为了很重要的东西，最终形成比如说 Cordis。然后我们的这里——就是 DeepSeek Harness 在第四个提交的时候实现了对 Cordis 的 merge：everything is a plugin，他把这个 plugin 在 Cordis 上面放进来。然后他又开始大量实现：先实现 LLM 的 inference，然后做了 agent loop，就开始一点一点。所以你看每一步都是小的。如果你愿意追溯这个整个发展的历史，在 AI 的帮助下你应该是能够学得会基本上任何东西的。

哎，这么快的吗？他还真的给我打了一个航母的比喻吗？看一看：2026 年 6 月 10 号到 20 号十天的时候，把可回放的会话做成唯一的 source of truth；Cordis loop 与适配器分离——这个他打了航母的比方，这是我不想要的对吧——把一个能跑的循环变成一个在真实机器上安全地跑：不是新增多少工具，而是把进程、文件、终端、云服务器做成抽象；然后增加这些 guardrail，包括超时、取消、溢出。然后他有一次重要的：从 7 月 19 号到 8 月 6 号，从终端到浏览器——它终于决定——这也是一个很重要、非常非常重要的决定。在一开始的时候他可能就没有想到：虽然 everything is a plugin 肯定是对的，但他没有想到如果用浏览器这个框架加上一个 DOM tree 会让界面变得非常容易扩展。也就是这个非常重要的决定——他造出……我觉得这个比方还是有点对的：这就是飞行甲板——就是从船（船是很通用的，可以载货、可以载人）变成了航母，放上外部的甲板，我们就可以在上面实验各种各样的飞机等等。当然我觉得这个肯定还是有问题的：如果你真的去看比如说一个一个提交，他肯定还是漏了很多有趣的东西。

我这里总结了这个提交历史里面其实有非常非常多的宝藏。比如说这也是 AI 给我总结的——我让他从里面总结各种他好的这种演化里面的工程实践。然后他第一个就提到了：设计有由来——从 RFC 到 ADR 到 Agent Notes。你们知道什么是 RFC 吗？你们都知道 IETF 吧——比如说在网络里面经常有……我给大家看过：RFC 是那个 Internet Protocol 的总的架构；然后你们在网络里面会看各种比如说 IP 包的……所以 RFC 是 Request for Comments，也就是说实际上是一种类似于草稿：如果我要做这件事，比如说我要做一个重大的决定——我是不是要把 TypeScript 扔掉？比如说我的 event bus 应该怎么样设计——那就是一个非常重要的设计。那他可能不会——我们每一个人都假设做这种重大架构决策的时候可能会错——所以他会先放一个 RFC 上去。所以在项目内部也可以有这样的 Request for Comments；然后可能内部的几个小团队就开始讨论。其实我们也有：我们在做我们的项目的时候会把它放在飞书上，一个共享的文档，然后大家就先 comment；comment 以后需要开会的时候就坐在一起直接开个会；直到最终大家讨论完了以后——甚至我们可以做 MVP：现在我们比以前要好了，以前开发的成本很高；现在我们一旦有一个想法，就可以直接许愿一个、再另开一个另外的分支…

然后完了以后看一下效果；效果以后直接把所有东西都砍了，回头再慢慢来；然后直接到一个 ADR——Architecture Decision Record。所以举一个重要的从 RFC 到 ADR 的例子。Rapidly 对吧——看看他有什么有意思的例子。完全没有准备啊——但是你看他在读了……他比我想象的要慢一些，还好。

他有一个问题：系统提示词 system prompt 存在 request header 里，其他消息存在 surface 的事件里。哦我知道了，这是一个架构上的问题：就是说他在设计这些系统的时候也会一开始「就这么做吧」做；然后做了以后发现最好还是用一个统一的抽象或者什么来处理。你看他就遇到了一个需求：它支持对话中途替换 prompt——模型需要往历史里追加一条 system role 的消息；prompt header 里——如果他之前的那个架构在 header 里，就没有办法解决这个问题，所以他就需要一个架构的重构。当然这看起来相对来说还是小一点对吧——比起比如说我们要在航母上加一层飞行甲板，这个肯定要小一个量级；但是他对于这个 subsystem，比如说对于模型上下文的管理来说，也是一个非常重要的设计决策。对，然后这个时候代码是不改的，大家讨论这个东西应该怎么样；然后到后面 9 月 5 号的时候——那个时候可能已经在内测了——他做了这样的提升为 ADR，然后后面再去做实现，进入 implemented 的阶段。它有一个状态机：一个状态机对不确定的、就需要长时间运行的任务；它有一个 agent loop 的状态，这个 loop 状态也在整个 git repository 里。对，设计有由来。

然后协作有边界——这个大家都看到了对吧。这有多少个提交？现在一共有多少提交了呀？真的，以前我们要做这个事要写多少脚本对吧——我们以前写一个脚本，然后我们还很聪明地自作聪明用「人脑计算机」去想我应该 grep 什么东西、然后 word count——然后我们发现这么多生命都浪费了。当然可能某种程度上是防止这个脑子生锈的一些练习——我一直说嘛：当你打开 Unix shell 的时候你就是程序员，所以你一直练习编程的时候你其实得到了一些 practice。你看有 22000 个提交——一个一个小的提交。然后他有他自己的协作模型：比如说我们现在团队小的时候，我们其实是一个 linear history，没有 merge——没有 merge 带来好处，真的是每一个都是一个单独提交；但是如果以后比如说有 external developer 的话，那会变得非常麻烦，因为我每次 main 动了以后所有的分支都要 rebase，rebase 以后要触发所有的 CI 流程——这会带来一些小的麻烦。好。然后他还有一个验收的层次：逐文件 100% 的覆盖率，还有一些真实产品与发布产物的验证，等等。提交历史里面其实有很多宝藏——非常非常多的宝藏。我应该还有非常非常多宝藏，我就不一一给大家讲了。

但是所有的这些——就是这些由人类保证的东西——都没有办法阻止 AI 生成 AI Slop 对吧。你们用过——谁用谁知道——AI 一定会：就只要你不说清楚的事情有两种。一种是如果你用了那种什么 grill me 那种技能好——如果你用了，他就疯狂地问你一遍一遍一遍，问到你烦为止你就算了；如果你不说啊，还是就会猜——他会想着完成任务，然后去做很多甚至不必要的测试验证，因为本来你要做的事情本来就是实验性的，他可能没有你的上下文，做了很多东西，让维护和修改变得很复杂。所以最终其实 DeepSeek Harness 这个项目还是由人来驾驭的对吧。然后为了防止 AI——因为人显然不可能在短时间内做成这样那么大的东西，就相当于是极速造航母对吧——有一种这个感觉——为了防止 AI 毁掉整个项目，我上次课讲了一个国际化的例子对吧，i18n 的例子：像我的 README 有中文有英文，这两个文档是严格保持一致的；然后靠一个这样的——我觉得很脏、非常脏的一个 YAML 来处理，起到的效果对吧：至少他阻止了文档的不一致，但他也付出了代价——repo 膨胀了，然后有一大堆意义不明的 YAML 文件。当然我可以在 IDE 里面配置它对我不显示这些文件，就眼不见为净，但它实际上存在的。所以其实这也是我前面就说：软件项目不应该用目录来存储——软件项目里面有很多复杂的东西，它们之间是有关联的，我们应该把这些关联给存储下来，而不是……当然我现在比如说用 YAML 存储这些关联对吧，但可能用文件只是一个 workaround。

实际上 DeepSeek Harness 做了非常大的工作去生产与人类对齐的好代码。那它的办法是什么呢？没有好的办法——找到所有不好的特征，一个一个强行排除。也就是说我们没有办法真的阻止 AI 生成 slop，那么我们就想到 AI 会生成什么样的 slop，就给他写一个验证器：在比如说 commit 的时候，或者 push 到 remote 以后、它每日 run 的时候，去检查你的 AI 有没有犯什么错误；如果犯错误，我就可以比如说阻止这次提交，等等。

比如说我在生成这个——很有意思——我在生成这个 DeepSeek Harness 的……我让他总结 DeepSeek Harness 里面的这种 gatekeeping：怎么样阻止 AI 生成比如说不合适的代码并且逃到 repo 里面——他所做的努力。然后他就激活了里面的——刚才对，激活了一个 dsh-prose-standard skill。我们可以先看一下：你看他有一个 skill 对吧，是文字编写的规范，有一点 anti-slop 的感觉对吧——他要删掉推理的过程、重复和修饰。如果你用 AI 写文档你就会发现：他会把思维链里面的东西——他自己想这个东西要这样设计、然后怎么验收、不要什么——都会写到你的文档里面。然后这是一个非常糟糕的行为。为什么呢？因为当 AI 开始写这种文档的时候，他写一个文档说「我做了 A、做了 B，然后又不是 C」——那么所有的这些 A、B、C 实际上都和比如说 `implement.ts` 就关联起来了；然后当这个实现改掉的时候，文档和实现就必须要同步修改——它其实引入了这种同步修改的代价。而实际上你如果看 AI 编程的话，如果它迭代几轮，这个中间可能这个 A 和 B 没有了——可能这个代码确实没有了——但是这个「不要 C」就被错误地留下来了；就很多不该留下的东西在软件演化的过程当中就被留在了 repo 里面。所以他就有一个这样的——甚至还有一个判定的基准。

我们来看一下 DeepSeek Harness 里面的这些 checkers——一共有七类：包括代码与类型的质量、架构与依赖的约束、行为正确性、持久化和兼容性、文档、构建交付和评审对吧。嗯，首先这就是所有的项目都应该使用的——虽然你们可能而不使用的——这种 lint 和类型检查的机制。这可以把很多的低级错误——对，虽然模型能力很强，但是不代表他不会犯低级错误，尤其是在比较大的代码库里。它有一些额外的：比如说改了接口，所有的调用方必须一起改对吧——这个编译器本身是可以找到的；然后我还要检查所有东西都能编译。我相信你们自己开发自己的项目的时候肯定不会做这么严格的检查对吧——你可能自己编译过了，发现有一个地方要改一下，你就这样改一下，你就把它 push 上去了；但是在一个真实的项目里面，你为了防止 Agent 干出这种事情来，你还是会有这样的各种各样的检查。新增不同用途的 id 不能因为都是字符串就混用；让静态检查同一份代码都遵守同一套 lint 规则。对，我们可以介绍一下项目里对 lint 的使用：在自动检查中会检查……你们在学第一门程序设计课的时候，老师有没有教你们用 lint 工具啊？这个我觉得不教显然是有很大的问题的——这就会让你们写出这种什么 `a = 1` 空格一这样的代码，这种事是过不了 lint 的。

类型安全与异步正确性：他这里能检查丢失的 promise 对吧、异步的不回收、过于危险的断言、no deprecated 对吧。对于一个——这对于你们自己的 hobby project 来说，任何不安全的特性都是可以使用的对吧；比如说如果在一个严格的项目里面打比方，在某些包里面他认为不可以引入 unsafe 的时候，Rust 就禁止——我可以加一条这样的 rule 禁止你使用 unsafe。嗯，这样你就过不了——就相当于你第一次实现或者 Agent 做实验性实现的时候可能可以用，但是它永远不可能把这个东西通过 lint 检查并且推到远端；它必须要再改再改再改，直到把这个给做好。对。No unused variables——这是一个非常有用的 lint 规则，因为一般来说当然这个对人来说有用，对机器来说现在还好。如果一个变量定义了不用，很有可能是 typo。你们都写过那种 `for (int i = 0; i < ...`——或者应该这么说——`for i = 0` 对吧，`int i, j; i = 0; i < n; i++`，然后可能或者有一个 `j++`——那这有一个 uninitialized……这个编译器和 lint 都会报错。如果比如说你就写一个比如说 `if (j)` 或者什么——你们都写过这样的代码对吧，i 和 j——那 lint 就可以帮你找到。Prefer const、no var、no unused expressions……作用域的检查。唉还有——你看还有很多严格的要求：verify export data is stock——每一个非第三方库导出必须要有 JSDoc；禁止硬编码 UI 文案；verify runtime、closure、climb domain graph、Cordis config——这都是一些和项目相关的。

好，然后在整个流程里面，在 pre-commit 的时候会做一系列的这种检查，包括刚才我们说的那种 i18n 的配对——就是你的文档中文和英文必须要保持一致；如果不一致，那个 commit hash 对不上的话，这个 pre-commit 就直接——就直接拒绝了。然后 pre-push 的时候会做 type check；然后在这个 CI 的时候可以做更复杂的检查。对，还有很多这样的这种检查，防止 Agent 一不小心——比如说今天啊也有可能啊——他就说我要实现一个功能挺好，但是他没有遵循这个你项目架构的约定，他就莫名其妙完整地把这个功能实现了一份，然后直接在你的那个代码上面添了一行函数调用直接就调过来了，第二天就回来了，破坏你的架构——他没有遵循你的架构，因为你没有对吧——你的提示词里面可能没有说「请严格遵循我的架构，所有东西都要这样用」——因为你写这句文档显然对人类来说是没有意义的：因为当你做了一个干净的架构以后，你默认所有人都要遵守。所以你的选择就是：你要么就把这句话写进去——写进去以后你会污染上下文——不能说污染上下文，它写进去后可能会有用、会让指令遵循变得更好，但是会让你的文档变得人类更难读对吧——你总是需要做这样的取舍。然后在这些时候，比如说我可以做一个控制流上的检查：我要求所有的控制流都是由我的插件发起的，这样如果 Agent 不小心写进了一个直接硬编码的函数调用，我就可以把它拒绝掉了。这基本上就是靠你的开发者的经验和直觉，一点一点把这个各种每一个细小的地方都写好对吧。浏览器代码不能无意间依赖 host 实现；浏览器应用请求相对于当前文档解析；网络调用不能悄悄要过、是绕过用户代理；wander 的更新应该怎么处理……还有测试——测试我后面会专门来讲——他也做了一系列的测试的这样的 gatekeeping 文档。嗯好。这是 DeepSeek Harness 里面的一些我觉得做得很好的地方。

你们有——我就觉得给大家点启发。我肯定没有办法在课上一个一个讲过来。首先，它和一些具体的项目、具体的语言肯定是绑定的，以及这个项目本身的功能是绑定的——我要讲的话就显得很枯燥；你们其实不是每一个同学都对 DeepSeek Harness 有兴趣对吧。我展现的更多的是一种：你如果遇到了一个你感兴趣的项目——比如说你是做 bioinformatics 的，你真的就想要靠它拿到你的 PhD——你就去看一下，把那个项目用我的方式来打开对吧。我教你们可以总结文档的质量保障是怎么做的，然后总结它的提交，把它化成一个这样的 commit 的时间轴——唉，也许就能帮助你更好地理解一个你想要学习的东西。

对，好最后呢：我觉得虽然我们已经尽了自己最大的努力，DeepSeek Harness 也尽了自己最大的努力，但是还是有很多问题没有解决的。就我刚才说：小事已经解决了，但是大事我们还需要一个 taste-bench。我觉得今天 AI 能力很强，但是他分不清轻重：他有的时候就过分自信，他就觉得这个事情他搞定了，其实他搞的没有达到我的预期；然后有时候他又过度小心——比如说这件事情其实不用那么小心的，但他就做了非常多的测试。然后如果你去纠正它——糟糕了对吧——你但凡说「不要这样」，他就会把「不要这样」写到你的那个……写到文档里：他首先在文档里写一份，然后在代码里再写一份，注释里再写一份；然后不断膨胀的这个上下文会不断抢夺他的注意力。这个「不要放蒜版」对吧——「不要放蒜版」——因为每一个出现在上下文里的词都会在模型的眼里认为是非常重要的；但其实这个世界里还有无穷多的词，我理论上说也应该出现在模型里，但是我没有把它写进去——他们的权重和「不要放蒜」是一样的对吧。我不要放韭菜、不要放蘑菇……番茄炒蛋你就给我炒一个番茄炒蛋——但是模型不理解它们之间的重要性对吧，或者说模型自己有他自己的想法。我们每一个人都有自己的偏见，然后人类社会就是靠我们的偏见向前进的对吧。

所以有一个启发。我以前是做这个 program synthesis——叫程序合成。然后如果我们想要合成程序——就想要比如说我们也跟许愿编程有点像——我给模型一个 spec，模型能把正确的实现给我。我说什么呢？我也有一个 spec，但这个 spec 可能是：我有一个函数，我知道 f(1)=2、f(2)=3、f(3)=4——所以你就会生成一个比如说这个 lambda x: x+1 对吧——你可能会生成一个这样的程序。合成技术大概在 2011 年的时候引起了一个小热潮：Excel 里面有一个智能填充的功能——曾经我上研究生课的时候都会把它拿来当案例来讲——它可以做什么呢？你可以做：你有很多不规则的电话号码，比如说 02512345678 对吧——比如说你从邮件或者从报表里面收集到的电话号码的数据，025 带区号，但大家写的不一样：有人就写 02512345678，然后有人写 025-12345678——你怎么让一个不会写程序的人能自动把它们归档成：对吧，归档成「都是 025 是区号、电话号码是电话号码」？这就是一个程序合成的问题，这叫 programming by examples：假如说我有些例子，你能不能生成一个程序——对于字符串来说你可以生成基于正则表达式的程序。然后还有 programming by demonstration：你能不能做一遍，他给你一个程序。当然今天这两个问题已经完全被大语言模型解决对吧——programming by example 和 programming by demonstration。

然后在那个时候有一个非常非常热门——甚至到今天还有人在研究——的技术，叫 Counterexample-Guided Inductive Synthesis（CEGIS）——就跟今天我们和大语言模型交互的方式很像。我有一个 spec 可能是这样的对吧，但是可能还有别的：比如说 f(4)=6，打个比方啊，但这个我还没有给模型——所以模型会生成一个 2x+1；然后我就告诉他：对不起，f(4)=6——x 等于 4 的时候等于 6；然后呢，那模型再去生成——然后这时候模型可能会生成：if x equals 4 return 6 else x+1。然后这就会陷入一个：你取什么样的 counterexample 可以让它生成一个正确程序——这很难。也就是说其实我们那个「番茄炒蛋不要放蒜」是一个很糟糕的提示词：因为你说了不放蒜，意味着你有同样重要的不放香菜、不放韭菜、不放辣椒……所以虽然刚才我们看到那个有一个——就是 DeepSeek Harness 刚才有一个处理文档的 skill——但是无论怎么样，这样的 skill——我相信大家用过——这是来自科学的 anti-slop。你们如果要写英文论文的话，这个 skill 对你来说非常有用：因为——对啊——我就不知道这是 GPT 的口癖，到现在可能都还有一个 ensuring、highlighting——对啊，我就你们就污染——就以前我们写文章不用这个词的、不用这些词的对吧：framing……我们有时候不太用的，虽然严格上来也不错；比如说「彰显」这个就太重了——我们从来几乎不也要谦虚一点——我们不会「彰显」something、showcase 对吧这些；然后有些 AI vocabulary：additionally、interplay、intricate 对哈；嗯，not just X but Y。好。然后这是一个非常典型的——对啊——非常典型的 counterexample-guided——就 sorry——就是这个过程：我们观察到 AI 会做 A、B、C、D、E，然后我就要求他做 not A、not B、not C、not D——但其实你那个 high-level 的这个 guideline 是什么，其实还不知道。

我做过一件这样很有意思的事啊。嗯，我希望——我们在讨论的是：有没有可能对吧，有一个 prompt 或者有一个 skill，可以帮助我们更好地阻止 AI 生成 slop。问题是这样的：我有所有我回复过的 email——有我所有回复的——但到目前为止，AI 自动帮我回邮件仍然是失败了：就说这可能是比较简短的邮件可能还可以，长的就不行了。我发现一个什么呢？我就算是把我回过的所有的邮件都放到模型的上下文里，说你就照着我的风格来，他也做不对——模型没有提炼这种东西的能力。所以我做了一个这样的 recursive self-improve 的这个 loop，大概是这样的：我希望有一个——我就希望有一个这种 anti-slop 的这样的一个 skill，但我不知道它是什么——比如说今天那个 anti-slop 是这样的；或者说我是 write email——然后我现在有一个可以检验的过程，就是他写出来的东西像不像我。所以我有好多的 email，或者说我有好多的人写的文稿；然后对于我来说我可以知道的是：我回复有多长对吧，然后我也有些比如说像词频这样的这种统计信息，然后比如说句子的长度、然后标点的使用对吧。然后我给他的 prompt 是：好，你可以 evaluate——相当于你用这个 anti-slop 或者 write email 的技能去写回复我过去回过的所有的邮件，但你不要看我回复过的邮件；然后我可以算出这些每一个 metric 它到底是提升了——是离我更近了还是离我更远了；然后如果离我更近了，我就会留下这一次；然后如果离我更远了，我就会要求他提取一条 general 的 guideline——对吧，一个不是这种说「不要用 not…but… 的句型」对吧——能不能想一个就覆盖广的、就能够覆盖——就不是「确实我确实不要蒜」，而是你能不能看透「不要蒜」的本质是不要无关的东西还是不要什么——能不能把一个这个 guideline 的 principle 加回到这个 skill 里，然后他的品味提升了。但今天还做不到。但我相信——就是我觉得我是乐观的——对吧，我今天讲了这个人类的这个过程：一个 isomorphic 的——不管是做软件也好还是做工程也好——一个流程。那有没有可能我们有一个 self-improved 的 loop，最终能把小事干好的同时，也把大事给干好。
