我们已经讲了很多软件工程的概念——什么是软件工程、什么是项目、项目管理——我已经说了一万遍，就不再重复了。正因为这些概念如此基础，在今天的 AI Agent Native 时代，它们又不断被重新更新。就在上周，Anthropic 说 Git 已经不够用了。其实我在这门课刚开始讲版本管理时就提到过：我们确实会有一天遇到不够用的情况，这很自然。因为上学时你自己就是一个 single-thread agent，学 C++、Python、JavaScript，写自己的项目；但当你拥有 Agent 以后，你立刻就拥有了一个和现代公司一样的架构——你就是那个 CTO，负责全部，但很可能不需要自己写代码。底下又有架构、产品、UI，前端、后端有好多个 Agent，每个 Agent 又可以带好多个 sub-agent，甚至 sub-agent 还可以再创建出更多的 sub-agent。其实你是在维护一个组织架构，否则不可能管理复杂需求。做一个软件工程产品，面对的是各种各样的 essential complexity 和 accidental complexity，这时候就需要版本控制，还是需要一个 repository，因为最终交付的还是一个产品，最终可能要经过 CI/CD 上线、给大家提供服务。

很自然地，任何人收到的都是一个 task 这样的小任务。从 first principle 去想，这个 task 一定和 repo 里的某些部分相关：可能要重构一个 subsystem，或在某处加一个功能，可能会影响到一些模块。各种各样的 task 在系统里的样子也不一样，覆盖的东西不同。所以 Anthropic 那个方案其实还没有用到——我说最好是给它加一个锁：有些可能是只读的（read-only），有些可能是 write，也有些可能是 refactor，锁的类型也可能变化。比如一个 refactor 类型的，或一个 minor 的 fix 类型：虽然它是写锁，但对架构不产生 breaking change，所以多个互相独立的小 fix，其实应该可以并行执行。虽然可以说借鉴操作系统里的锁（先上锁），或数据库里的锁（先做再做 conflict detection）——乐观的和悲观的——我们应该怎样设计版本控制，其实慢慢会从组织架构上得到答案。但可以毫无疑问地看到，世界在向这个方向推进。

因为概念已经讲得差不多了，我们还是应该回到一个比较具体的项目上，看看如果真的要设计一个产品，整个流程会是怎样的。肯定要选一个 Agent Native 时代的产品，我就选了 DeepSeek Harness。正好前天在北京参加了他们那一次线下聚会，很多同学就是像你们这时候这么大，可能也不像我这样写过很多代码、经过古法编程时代，可能就是对着 web 去许愿编程，但他们愿意到这里来跟大家交流，很有意思。经过几年成长，他们就会成为非常核心的开发者。所以我觉得有必要讲一讲：如果要从零开始构建一个 Agent Harness——当然不会做成那么复杂——你们会遇到什么样的问题，再从这些具体案例上讲解这件事情到底怎么发生。里面有很多细碎的东西，今天会讲到需求、架构，以及整个软件系统的设计会是什么样的，我们怎样在 DeepSeek Harness 上做二次开发。下一节课我可能会讲整个 Agent Native 开发更细的东西，因为 DeepSeek Harness 里面有非常多的 CI/CD。

我看到有同学在评论里讲：上节课讲了很多，但看起来好像什么都没讲。确实是这样。因为有些事说起来简单：网上有很多 skills，你可以 grow me，可以 grow with stocks，还有 Superpowers；但真正拿过来用时你会发现——比如用 grow with stocks 去做那个 L1——马上就陷入无穷多你不想让它管的事情里，尤其是面对未知的时候，你不知道它在干什么。有时那个 skill 会反复疯狂地 find out、spawn sub-agent，做一些你可能觉得没有必要的测试或 validation。这些东西在某些场景下——比如真的在公司里开发产品——是成立的，但你们最好自己摸索一下，有一个切身的感受。所以我今天也为大家切身摸索一下：我已经把编译好的 DeepSeek Harness 准备好了，应该可以正常工作。就是一个 DeepSeek Harness。不知道你们有多少同学使用过一个比较复杂的开源软件，并且真的动手改过它。在 pre-LLM 时代，把它运行起来都很困难；但我现在完全是许愿式运行——从昨天到今天，我在这台机器上部署它，包括外部的一些东西，全部都是许愿式的：只要知道这个项目可以被编译，OK，让它去做。

假想我们要实现一个 DeepSeek Harness，应该从哪里开始？肯定是从上一节课的 mini-agent。大家应该还有印象：这就是一个 Agent Harness。几乎所有的 Agent Harness 都遵循这样的循环，因为大模型推理是 Responses API，不管返回工具调用还是什么，都是一问一答——不管回答的是人还是工具。那这个 Agent Harness 能用吗？能用，它完全可以工作。周日我在高铁上突发奇想：既然我们要讲 Agent Harness，能不能让我们的 Agent 生成一个真正不 trivial 的任务？这个任务可能确实会比较长，正好新模型也发布了，我就给它一句话——真的是一句话：我要一个比例基本真实的南大仙林校区三维图。

你们有没有预期到它会输出这样的结果？还是很不错的，虽然有些地方不太对。比如计算机楼是十层，但高度明显做得不对；有些又做得相对正确，比如图书馆的建模相对比较好，尤其是楼从 top-down 来看，几何形状被正确保持了。如果你观察 Agent 的 trace，它是怎么做到的？因为网络上有很多数据源。其实在我上学的时代就发现了这个宝藏：有一个网站叫 OpenStreetMap，开放的地图，能找到各种各样地方的地图，而且很细——比如如果这是一个篮球场，它真的会划出篮球场的线。它还没有用全部的模型，从那里爬了数据，爬完以后自己根据想法建了模型。有些想法就不对：地图上可能没有东西的部分标上了绿色，说这是一块绿地；绿地可能有小公园或可以休息的椅子。大门也被化成了楼；大门进来的地方铺满了树。所以仔细看看可能不太好，需要给它更多提示词，比如说：让你把每一块区域都单独划定出来，划定以后仔细思考这块区域的功能、它应该是什么样，再做一个精确的建模。它会花更多的 token——十倍 token——再修一点，就可以得到更好的版本。你在网上看到很多不管是用 GPT 还是 DeepSeek，说 DeepSeek Flash 新版图形能力很强，也都是用这种方式：有一些 skills，不停追着让它一遍一遍验证，通过烧 token，从一个还不错的基础上，最终可以得到更好的结果。比如我相信很多同学都梦想做一个南大版的 GTA，可以在里面身临其境——如果你想的话，这就是一个很好的 starting point：你有三维模型了，还可以 instruct 它去构建什么地方可以走人、什么地方可以蹲点，就可以构建游戏的逻辑。

这完全可以工作——作为一个在课堂给大家玩一把的 demo 肯定可以，但不能作为一个产品。因为上一个版本假设了网络服务不会中断。如果你只是一两轮对话，其实感受不到这个问题；但我在高铁上大概已经跑了比较长时间、有些中间结果了，突然网断了，进程就直接终止了。我那 150 行的 mini-agent 没有会话保存，也没有恢复，也没有写网络中断以后重试——都断了以后，我就只能要么从零开始让它继续，要么让它重新再做一遍。这其实就是 essential complexity。你再往后想：如果要做一个真正的 Agent 产品，比如一个 DeepSeek Harness，怎样应对 API 中断？首先就是需要重试。你们都见过 coding agent 的各种重试行为。这时候又需要：重试到底要有多少间隔？因为不同环境下不一样——在美国数据中心访问 OpenAI 的服务，和在中国挂上一万层梯子访问 OpenAI，网络环境不一样，timeout 等也不一样。所以 API 中断时，设置重连或重试的时长、连接中断的时长，又变成复杂问题。一次失败以后，第二次应该以等间距再试，还是慢慢拉长时间间距？学过网络的都知道有 exponential backoff 这种探测特性：一秒钟失败了，再一秒钟还失败，大概率下一秒还是失败，所以可能要等两秒、四秒、八秒，直到网络可能是以分钟级——像我刚才那种物理世界故障，启动就可能需要两三分钟才能重新回来。那都是非常大的复杂性。我让 AI 帮我总结一下，它还说出了更多莫名其妙的东西。

在实际产品当中，你还会面临更大的挑战。比如服务端和客户端可能不一致：客户端发起一个请求，比如说支付，服务端收到以后就把订单下了，因为它还涉及和其他系统的确认，不能等你把所有做完、transaction 由你来 close——收到以后才把 transaction commit，它做不到。因为这可能是你订下一个淘宝单或买一张机票，钱送给银行或航空公司时，transaction 就已经结束了，所以会在服务端完成；服务端有非常复杂的架构可以支持可靠的订单完成。但订单发出去以后你的手机就断网了，怎么办？设计产品时你会看到手机上转圈圈，应用不能 crash，得告诉你网络中断了，所以现在这个订单处于一个我不知道的状态——可能下成功了，也可能失败了，但因为和服务端缺少同步，它不能决定自己到底是什么状态。所以我们现在在软件系统设计时，有很多这种 essential complexity：它就是复杂的，没有办法避免。

如果你要设计一个 Agent 产品，不是 150 行的 agent，那就涉及到项目管理：Agent 同时可能在好几个工作目录上工作——不管是用 DeepSeek Harness 还是任何一个 coding agent 都可以做到——你就需要一个 dashboard，能在多个项目之间切换。Agent 还需要访问项目相关的工具、Skills；运行过程中工具调用需要有沙箱和权限。回想平时用 coding agent 时都看过：它问你像你要 approve 时候的那些产品设计。那就会带来一份非常非常长的产品需求规格说明书。我又让 AI 假装自己要做一个 WorkBuddy——这可能是你们老板的要求：公司今天要出一个产品，对标现在卖得最火的和人交互的 Agent；调研一下 DeepSeek Harness、WorkBuddy 谁卖得最多，WorkBuddy 卖得最多，你就去做一个。如果要这样，你会看到 AI 还是挺有智慧的。虽然我今天讲 DeepSeek Harness，它肯定走了一条完全不一样的设计路线，但 AI 确实想到了一些有趣的：先想一些典型应用场景、用例图之类的——「把这个文件夹里的本周项目记录整理成周报，列出延期事项，生成 Word 文件」——这是办公管理里非常常见、普通人用的场景。然后在这个基础上列举潜在应用场景，开始疯狂列需求点：历史检索与任务复用——这是 Agent 产品需要完成的非常典型的功能——模板与偏好、执行预算与用量、账号与数据管理、外部内容与指令隔离、用户反馈与问题诊断。当然实际上还会多得多，还有很多非功能性需求。

如果你直接让 AI Agent 去实现这个需求，大概率就会陷入 AI Slop 的状态。因为 Agent 有一个非常强烈的倾向：要直接把任务完成，不会动脑子去想未来还会发生什么。所以做一个产品和做一个 MVP 其实不一样；但 MVP 可以帮助你看到产品到底有什么真实需求——在使用 MVP 时，你的假设会不断被 validate。像我的这个小 Agent，就做了一个不切实际的假设：网络是稳定的、API 是稳定的；这个假设不成立以后，需求其实就相应膨胀了。所以如果我们要设计一个 Agent Harness，面对的真正挑战，其实是需求的改变。

比如说刚才我们已经做了一个面向 WorkBuddy 的办公场景、非常详尽的需求报告，你已经带着 Agent 写了 50 万行代码并且上线了，然后突然今天 Grok Bot 火了。Grok Bot 是一种新的交互方式：我们可以把 Agent 当人，每个人有自己的记忆；可以拉一个群，让两个人一起协同完成工作；也可以让人每天什么时间干什么事。这些都挺好。但 Grok Bot 火了以后，你会发现它的交互方式和刚才我们做的那个需求完全不一样。我们做了非常详尽的需求：左边栏是项目，右边栏有几种，比如什么 pinpoint view、什么 will。如果有一天老板突然说，下一个版本就按照 Grok Bot 做吧——什么叫怎么杀死一个程序员？你只要改需求三次就可以了。因为之前所有需求的假设全都崩塌了，交互模式的根基崩塌了。所以应对需求的改变是非常有意思的事情。

不管大厂做了多么好的架构——在性能上可能达到极致，在功能性、非功能性需求上非常好地满足上一个版本的设计——一旦这种摧毁性的事情来了，大厂就必然要开始疯狂拉通对齐、闭环沉淀复用，再到下一个版本。这确实没办法：大厂毕竟有交付质量的要求，它做了一个选择，期望极高质量地交付需求，所以架构可能会相对保守一点。相比之下，就比如说 DeepSeek Harness——我没有装它——但当你看到就是光速地不止一个人去 release 了这个 dsh-bot，看起来就跟刚才那个像素级复刻：可以设置多个 bot，可以拉一个群，甚至群还有像群一样的图标，非常真实，可以跟它聊天。光速复刻，而且甚至在这个基础上，你可以 vibe 出很多它没有的功能。Grok Bot 比如你今天觉得哪一点不好——我觉得它不好的是：它希望给普通人用，所以不给我开放任何编辑它的东西的权限、配置的权限；但对我一个 programmer 来说，我真的想把那个 configure 的 YAML 拿出来自己改一下，或者把 prompt 提示词给我改一下，因为我懂得怎么改提示词；但对 99% 的人来说，他们都不知道应该怎么跟模型对话。所以 Grok Bot 是一个很成功的产品；但如果你不满意，可以 vibe 一下，在这里加上别的功能，比如一个 multi-agent 交互的 dashboard。你想像一个老板视角——又回到这个图了——本质上 Grok Bot 是想构建这样一个组织架构：项目以项目组和人组织，你每次只要和项目组或者你的 CTO 交流——你就可以做 CEO 了——去把事情做了，再把任务一级一级分下去。那我有没有可能：左边不是这样的树栏结构，而是做成树状结构代表你管理的部门，让你有老板的沉浸感和体验感；右边也不要这样聊天了，压缩小一点，有一个老板视图，好像自己坐在办公室里，给你提供一点情绪价值。然后马上就有人可以去 vibe 这种需求。

为什么讲这个故事呢？我们把时间倒回到 2026 年 6 月 10 号。那还是 coding agent 已经达到大家意识到要变天了的时候。当时有一些主流产品：Claude Code、OpenCode 这些都有，还有字节系的；那时候没有 WorkBuddy，有 CodeBuddy。后来我知道 WorkBuddy 和 CodeBuddy 其实共享了一整个 Agent 层编排的底层架构。就在这个时候——我还特意看了一下——2026 年 6 月 10 号晚上将近 11 点（讲义写的是 22:57），谁说 DeepSeek 不加班的？有一个神秘的项目启动了，里面什么也没有。连那时候还有 Claude.md——这也是一个很恶心的需求点：当你需要支持一个项目同时支持多种 Agent 时，就需要用它们都理解的方式去组织项目文件。当然好消息是，今天你不需要用 Claude.md 了。然后做一个 link：MVP requirement analysis，有一个 microkernel architecture。你看他从第一天开始，6 月 10 号晚上 11 点，就想做一个操作系统，想造一艘航母。那这航母到底是怎么造出来的呢？我们就要回到讲一讲架构。

刚才我们说：如果你直接对着需求文档，让 Agent 帮你做一个架构，那么 Agent 的注意力就会在需求上。需求很自然——比如这里面有一个东西叫工作区——那么 Agent 就会很自然地倾向于在架构设计里为工作区做一个 class，涉及到工作区和其他东西的交互。当然这个设计肯定是需要的：比如和模型、Agent 层的交互是什么；工作区可以链接到 Session（会话），Session 可以向 Agent 发送一个 chat；Agent 之间自己可以调用 Agent loop 或工具来做事，同时也可以把一些结果——一个绘图绘制的 canvas——放到 Session 上；然后这个地方应该用一个数据库来存放 Session。好，这个架构就开始出现了。这是一个非常非常自然的架构设计方式，或者说在大厂里面也经常是这样设计的。

但是架构意味着什么？架构就意味着没有免费的午餐。当你做了任何设计以后——不管是这样的架构，还是可能 DeepSeek Harness 那样的架构——架构都是在受限和自由之间达成一个平衡。架构确定了以后，模块和模块之间的边界就有了；边界有了以后，你就可以在开发这个模块时不用知道、或只要比较少地知道系统剩下部分是怎么工作的。好处是：第一天需求就分成了这样的架构，分好以后每个模块就可以独立开发，马上就可以启动大量的 sub-agent，把产品给堆出来。但你做的这个限制就限制了自由度：当未来需求发生改变——比如 Grok Bot 这样的需求出现——如果你的架构不能适应那个未来的需求，就会不断有抽象泄漏，导致项目很难维护下去。但如果你做得太自由，说我要做一个创新性的架构，每一个模块都是一个 process——不管是工作区、Session、Agent 还是 UI，每个都是一个进程，进程之间都是发消息的 message passing——那这个架构就非常干净、非常自由，我可以随便发消息。它自由，但这个架构没有任何用，就是个 actor model。说得很对，可能确实能这样实现，但它没有约束，比如消息应该怎么管理；不像那个架构一样，说工作区和 Agent 之间通过某一个 API、某一个队列——比如一个 Session 的 message 队列——来管理。接口定下来以后，就只能做这件事，比较容易开发；但如果自由的话，什么时候发什么消息都没有确定，等于没有架构。越自由的东西往往越不好开发；受限有受限的好处，自由有自由的好处。所以带着这个想法去理解所有的架构系统：一层一层架构的设计，都是有取舍的。

比如说操作系统上面的进程就是一个非常好的抽象，但它非常自由——当然它就是为了让你在上层自由搭建各种各样的应用程序：可以做浏览器、coding agent、虚拟机、做任何东西。操作系统要提供这样的功能，但这自由也就意味着：就为了到底要用什么编程语言开发这件事情，人类吵了几十年——到底什么语言才是最好的编程语言。现在我们好像这个老梗——说 PHP 是最好的编程语言——已经见不到了；这个梗在我上学的时候还非常流行。高级语言也是的：你做得越自由，C 这样的程序就可以更好地控制机器，但带来的问题是可能有内存泄漏等各种麻烦。受限和自由，你没有办法达成一个完美兼顾，只能在这个 spectrum 里面做一个取舍：限制做到什么程度、自由做到什么程度。其实每一个架构都有这样的问题。

比如说经典的 Linux、Apache、MySQL、PHP——PHP 是世界上最好的编程语言——它是一整套方法的架构，引领了整个互联网世界至少十几年；WordPress 就是个典型。但当你要服务更多人——服务一亿、十亿人的时候——这个架构就扛不住了：从单机到数据库，每一个点都是瓶颈。为了把它拆开，就各种抽象泄漏：先分库分表，让一个服务器扛着，最后服务器也扛不住，再拆开架构，就演进到了下一个版本。再包括 Event Sourcing：我们讲 Event Sourcing 可能比较好——所有东西都是事实，你只要 append-only 地记下来，剩下的人看到的都是事实的一个 derivation。架构概念很干净，但它也不是没有代价：当前状态完全由过去的历史推导出来，首先要把性能做好难度更大一点；其次有些时候我们真的只是想 hack 那个当前状态——比如说教务员就是想让你强行毕业，没有理由地想让你强行毕业——在一个月黑风高、没有人知道的时候，悄悄地你就突然毕业了。这种操作在真实世界中可能是一个合适的需求，但在 Event Sourcing 里面这件事就很难办到：你需要加入一个特殊的 event 和特殊的处理规则叫「强行毕业」；而强行毕业这件事情因为在 event 的 persistent history 里面又会被审计到，你又不能以「我也不知道那个时候是怎么回事」来搪塞为什么这个同学可以毕业——因为谁 committed 这个 event 当时就知道。所以这好像也是一件比较有趣、但有点危险的事情。

所以每一个架构都有取舍：他牺牲了一些，当然也得到了——可能是解耦合的系统，可能是 persistence 给你的好处，你甚至可以回退到任何一个历史版本。总原则就是：如果架构和需求是匹配的，你就是方便——LAMP 这样在单机还能够处理应用需求的时候，它就是最好、最合适的架构，PHP 就是最合适的语言；但当假设发生改变的时候，这个架构就可能会成为阻力。我觉得某种程度上，人类社会的进步就是不断打破旧假设的过程：新的产业要诞生，旧的产业要消亡；新旧交替时就有人才的流转，有些人自然而然被淘汰——老登们就被淘汰了——大家在接纳新事物的时候就有新的机会诞生。你们每个人都会经历身边发生这样的事情，最终才能真正开始理解。比如我小的时候经历过很多次，包括我们国家很大的变革——国企改革你们可能只能听说过——再到房地产的崩盘，再到 AI 时代的来临：我们从互联网时代、云计算到 AI，每一波浪潮都有这样的新旧交替。这也是一种架构上的变化：架构和需求匹配时就便利；假设发生变化时，你就需要一个更新的架构。当然我觉得在「AI 是产业超级加速器」的今天，这个变化会变得更有趣一点。这些是 AI 帮我补充的，你们有兴趣回去看 slides 就行。

然后我要讲一个具体的架构变化案例。在 2004 年的时候，Jeff Dean 和 Sanjay Ghemawat 发了一篇文章，某种程度上改变了 LAMP 那种中心化服务器的浪潮。这篇文章叫 MapReduce: Simplified Data Processing on Large Clusters，非常非常好读——好读到你只要看例子就行。说如果我们要做大规模分布式计算，不要去写好长好长的代码，只要遵照一个受限的代码模式，叫 map 和 reduce。这是 functional programming，Python 里面也有：map 说我有一个 list，再有一个 function，就可以把它变成另外一个 list；reduce 说我拿着一个 function，不停地 f、f、f——先拿第一个元素，再拿第二个……但如果这个 f 有一些比较好的数学性质，比如有结合律，就可以 parallel reduce 两个部分，再 reduce 它们的结果。如果你能把计算写成这个形式，你就可以用我的框架。所以他做了一个架构上的取舍：限制了你的编程模型，你只能这样写程序——先 map 再 reduce。当然 reduce 的时候有些比较聪明的设计，比如会把东西按 key 排序等等，有一个排序、shuffle 的中间过程；然后剩下就是他做了一个系统实现，藏在后面，你不需要知道它是什么。好处就是你只需要写这样非常简单的程序——早期在 Google 内部是 C++ 的，整成这样 include 一个 mapreduce.h，然后就可以写一个 class，里面说 map 是什么、reduce 是什么，就像写正常程序一样，只是你使用的不是程序里面基础的 pointer、list 这样的抽象，而是一个被系统包裹的、可能会跑在不同机器上的抽象。

然后就可以写出这样的代码：我们在一个分布式文件系统上做计算，可以说我要 MapReduce，最多 2000 台机器，每台机器用 100 兆的 memory per task，然后跑吧——它就可以自动在很多台机器上跑完 MapReduce。所以这是一个引领了这个世界的设计。后来大家发现：原来有这样的抽象层，写分布式程序就真的变得容易了，而且还可以容错。Google 那个时候遇到的最大问题是：有很多台机器时，整个系统就变得不可靠；当运行一个很长的任务——比如整个互联网全数据的索引——几乎一定会有一台机器掉线或出故障。以前 LAMP 的基本假设是这台机器是好的：你们每个同学在电脑上做大作业时，基本假设是「我的机器不会突然消失」；如果机器突然消失了，你就摆烂，跟老师说对不起——用社会工程的方式解决。但 Google 不能用这个方式，它必须用 system 的一个抽象来解决问题。它成功了，也失败了：因为这个限制只对这种离线任务比较合适；第一个其实用起来不是特别方便；第二个如果你想更方便地处理及时来的数据——比如银行的订单——当这些需求也走向分布式时，MapReduce 就没有办法支撑它们了。所以我们需要更高效的架构。今天的答案是 Spark 这样的计算引擎，还有 Flink 这样的流式数据处理；Flink 其实和 Event Sourcing 也有千丝万缕的联系，也和 functional programming 有千丝万缕的联系。这是一个具体的历史例子。

所以我讲了那么多，是要说一件事：架构是受限和自由之间的平衡。那如果我们要设计一个 Agent Harness，first principle 是什么？我们看到第一个提交上面说：我们要做一个 microkernel，做一个操作系统。操作系统意味着什么？意味着操作系统不需要知道每一个进程是干什么的。UNIX 诞生的时候还没有桌面浏览器，也没有图形用户界面，它不需要管、不需要知道这个进程是干什么的，但能把这些进程组合起来，并且进程之间可以互相组合、互相使用。所以他的 first principle 是：**Everything is a plugin**——所有东西都是可以插件解耦的。每一个 plugin 有点像 actor model，但它并不是一个 actor model。你可以这样理解：如果把每一个插件都想象成一个进程或一个人，让他们之间互相发送消息，理论上说是可以实现任意架构的。这个架构只是说：我希望把每一个模块的 private state 都封在自己里面；当模块和模块之间需要交互时，你就给我发一条消息，我可能会给你一个返回。所以理论上你可以把任何软件系统的模块都当进程提取出来，把模块之间的函数调用换成 remote procedure call，任何一个软件都会变成这个样子——所以这个架构本身是没有用的。

大家都在谈论 DeepSeek Harness 的时候，他先发了一篇论文叫 Cordis，里面有大量的公式。虽然 Cordis 也是架构的一部分，但今天我不讲这个部分：因为 Cordis 负责的是服务的解析、依赖的激活，以及这些插件的 load 和 unload。这就相当于：如果把 DeepSeek Harness 想象成一个操作系统，那上面的东西就是进程；我们知道操作系统里面该有进程管理——进程退出时，所持有的所有资源都应该被回收——这是大家已经默认了很久的事情，就像你们写 OJ 从来都不回收里面的内存，因为知道操作系统会回收。而 Cordis 的设计就这个想法：当然它不可能把所有 side effect 都能回收；理想情况下，你的进程可以 declare 它需要一些资源，或者说它对系统会产生一些 side effect——比如可能依赖一些东西，依赖应该被自动加载；而当我的插件 unload 的时候，依赖的东西最好能够自动卸载。就像操作系统在创建进程时会分配内存，进程被 kill 掉时也要自动回收。那这显然是 plugin 的这一层。

但整个 Harness 设计真正的难点在于协同：这些插件之间如果让你随便发消息、随便协同，那就全乱了，没有任何实际好处——就跟我说每一个都是一个函数、链接在同一个地址空间里面没有任何区别；不协同又没有用。所以真正比较有意思的设计，是你要构建一个 Agent Harness 的世界模型。DeepSeek Harness 里还有一个非常重要的、相当于所有进程共享的共享空间，关键的数据结构都存储在这个空间上；基于这个，DeepSeek Harness 还构建了更多的抽象。他没有特权的内核，所有东西都是 Cordis 的插件，但这里面有更细一层的世界模型：比如 core 下面的 Session。如果我们要做 LLM Agent，还是以大模型为中心的应用，无论如何还是以大模型为中心，所以他的 Session——append-only 的 session event 日志——是唯一的 ground truth；模型的历史不是存储的，而是从 deriveMessages 派生的。也就是说它有一个相当于完整的事件日志——这就是 Event Sourcing，他也用了 Event Sourcing。所以他在这个进程的基础上，又做了一个 event bus；插件还可以监听这样的 event bus。然后在这个世界上有一个 persistent history，所有其他能力都是在这个基础上长出来的。他会做一些类型检查，有 service definition、provider 和 consumer，以及一系列的权限管理。最重要的是：事件是扩展点，按领域分类。也就是说系统里面每一个插件都可能产生一些事件放到这个 event bus 上；上面写的那些大部分是用来规定消息的格式是什么、谁能够往 event bus 上放东西、类型匹配不匹配——如果不匹配，TypeScript 是不会编译这份代码的。他做这样的限制，就像禁止你任意往别人那边发消息一样，架构上面要做限制。然后我发完消息以后，还允许一个插件去监听另一种消息：当事件进入 event bus 以后，我的插件可以监听某一个事件，就会收到这个事件的 payload，甚至还可以去修改这个事件本身。所以它相当于赋予了一系列原子的能力——一个小的操作系统——每一个插件都在这个 bus 上可以看到，比如每一个插件都可以看到 LLM inference 的状态：大模型这次吐出来多少 token。当然还有一些设计：大模型的这种事实际上是不 committed 的，history 里面可以有一个 open 的 entry，代表这次还没有结束，所以大模型会不断往里面送新的 token；这个状态是不 persist 的，但依然可以被看到，这样我可以实时显示。比如你们可以看到 thinking——这里面不断有思维链动态变化。这其实是一个事件，但这个事件是动态的。这是一些小的实现细节、trick。

比如 LLM inference：我收到这样的事件以后，有的插件就可以用来统计 token 的 cost 和 cache hit 的情况，然后把它放到 UI——他又做了一层叫 slot、slot-based 的抽象，可以绑定到这个地方。所以最早内测版本的时候，这些东西都是没有的，原生真的就是白板一块、什么都没有；但是这个白板第一天就有开发者群里的同学：我们来有一个 token 统计、上下文统计吧——他就可以做一个，完全不需要干扰系统里面任何一个其他部分，因为这是一个不侵入的功能：我只需要观察 event bus 上 LLM 吐出来的 token 情况，相应更新自己内部的状态。所以还是这个模型：他希望把大部分的 state 都放在自己内部，只有希望别人看到的事情，才以事件的方式放到 event bus 上。这是一个还算非常自然的设计；但为了 LLM，显然做了更多的 specialization。比如说它有几大抽象：Session 是 list of event；Agent 是接收输入、推动执行；还有一些用于装配的 UI slots。基本上有这些东西，你就会想：所有 WorkBuddy 里面想要实现的东西，它都可以实现了。有些比如我想把它改造成一个 bot——DeepSeek Harness 有什么比较好的特性呢？如果你对这个聊天框不满意，想用换一种更 fancy 的方式来展示它，你完全可以：可以直接把这个 Session 流——因为你看到的这个窗口本质上也是从 message history 里面导出、算出来的一个东西——你说我不要了，设置成不可见，然后放一个我自己的东西。在 DeepSeek Harness 里面其实有这个 trajectory：你看它就是整个 session history 的两种不同类型的投影——可以把 history 投影成这样给人看的 UI，也可以投影成给 developer 看的 trajectory，可以调试里面：随便让它 call 一个 bash，你可以看到工具调用的 payload 是什么、干了什么、结果是什么，还有一些额外信息。所以你看：他就是白板一块；但在这个白板上，通过它第一方——这个第一方很重要——比如说如果他对 event 的设计崩了，或者对 Session 的设计崩了，那整个后面 DeepSeek Harness 不可能维护得下去；但如果他把这个概念体系建得很好，使得上面的插件绝大部分时候都只要 consume 非常少、对系统没有侵入的事件——虽然它有侵入的能力——我们就可以在上面实现任何东西。所以我当时看完、他发布以后就说：震惊、瘫坐、原子弹爆炸。大家可能没有意识到一个干净的架构可以给我们带来什么。他看起来很平常：比如 API 就是 Session——我可以在 Session 上面 append，或者注册某一个 event 的 handler，在 event bus 上去监听；或者从事实里面生成投影。我刚才给大家展示了：我可以 `session.deriveMessages()`，可以从 persistent history 里面导出 Agent trajectory，或者这个 chat——就光这个功能就非常好使。以及可以向 Agent 提交输入：可以 followup、可以 inject、可以 steer——这些都是你们在用 Agent 产品时用过的。比如用 Codex 时，模型正在推理输出的时候你可以继续提问；但这个继续提问：是应该等到这一轮工具全部完成以后再 inject，还是下一次工具调用——大模型那一轮 chat completion 或一轮 response 以后——就立即把新的 prompt 注入进去，还是按 ESC 停下来再来？这是 Agent 的操作。以及可以持续贡献动态的上下文；而 `ctx.systemPrompt.context` 这种、`session/event`——它可以 hook 一些还没有 persist 的事件：有些事件刚进入系统的时候我是可以篡改的。这个能力是整个系统设计里面非常关键的一环：它不再是说我只能看了、看了以后再推一个自己的新事件上去，而是我可以比如说把一个东西扔掉，或者在 `agent/pre-step`——在 pre-step 之前我可以干一些事，这时候甚至可以往 Agent 的 loop 里面 inject 一些 prompt。

你们想想如果在做需求的时候你会怎么做这件事：我希望每一轮对话的时候，都把当前我所在的时区信息、我所在的电脑的一些指纹信息等等注入到模型的上下文里——这显然是一个需求。这个需求你可以写在需求说明里，然后直接在 build context——如果要实现一个 Agent，一定会有像我那 150 行里面也会有的 build context——直接在那写一个；但我也可以在 Agent 的 pre-step 的时候放一个这样的 hook，把它的内容给改掉。所以基本上整体的架构就是：插件挂在一个总线上，有少量协作的接口；每个插件绝大部分状态都留在插件本地；但因为他们能够看到、感知到全局的 Agent loop、Session，以及可以看各种各样的 projections，所以基本上每个插件都能很好地感受到、按需得到他想要的所有信息——关于当前 LLM inference 到了什么进展、其他插件做了什么——整个还是以大模型的推理为核心。然后这个设计一切都是为了插件的生态。你们看到的比如这个 trajectory，只是它原生第一方发布的一个非常 plain 的特性，但对你 debug 很有用——如果我们是开发者的话。

在这个地基打好了以后，你会发现做任何东西都非常容易。比如说如果你想为他做一个 text UI：DeepSeek Harness 原生设计是 Web UI，因为 Web UI 里面有一些关键的抽象，比如装配 UI 的 slots，Web 可以呈现一个非常人类友好的界面；但如果你偏偏要剑走偏锋，说我就是不喜欢 Web，我就是喜欢在命令行里——像我上课时在命令行里面——那 text UI 是什么呢？就是你把所有用于装配 UI 的 slots 全都扔掉，只要有 Session 和 Agent：在 event bus 上只要能够听到所有 Session 相关的事件，包括这种 open 的 chat completion、他还正在吐 token，我只要能看到这些，把它投射到我自己的命令行终端上——整个 Web UI 甚至都不用动。我甚至可以做一个 Web UI clone 的、共享状态的 text UI：比如说我现在跟他说一个 hi，他在这运行、输出的同时，我在另外一个终端上可以看到一模一样的东西。结束了——一个非常舒服的 TUI。所以还挺好玩的。当时在内测的时候，最早 DeepSeek Harness 是有 TUI 的，然后 TUI 直接从 repo 里面移除了——最早官方 repo 里面有一个 TUI，然后被移除了，现在有个第三方的 text UI。然后像 pdf-reader 这种也是 hook 一些生命周期：当我看到一个东西的时候，比如说加载 tools 的时候，我就可以把我的 pdf-reader tool inject 进去，它以这种 event 的方式来管理。然后这些都不是这个插件生态真正好玩的地方。真正好玩的地方是：如果让你们来做，你们会想做什么插件呢？这不就是一个你们会说——这不就是 Codex、OpenCode，全部都长这样吗？我们还能干什么呢？

所以 DeepSeek Harness 专门给了一个——这才是去释放这个插件生态系统、或者说一个好的架构真正能力的地方——他有个 Creator Mode。Creator Mode 就和比如说 WorkBuddy 这样的产品就不一样了：WorkBuddy 说好，我有一个预先的需求，请所有人都在我的需求里面工作；而 Creator Mode 给了这个 Cordis 的权限。一般来说你的一个 Agent 的 Session 就只有 Agent 的权限——比如说这工作区目录的读写、bash，然后可能后面还会套一个沙箱；而在全火力全开的 Creator Mode 里，他是能看到这个世界的，可以把这个插件拆了，可以往这里面加插件——也就是说它可以在 Agent 一边运行的时候，一边就往这个 event bus 上面挂东西。这个能力一定程度上来自于 Cordis 的动态：它要求是一个全动态的插件生命周期，就有点像操作系统——我可以在操作系统里面随时启动一个进程，也可以随时把一个进程杀掉。所以你看起来他是一个白板，但实际上它是一个核弹。所以为什么不说许愿式插件呢？你就可以许愿插件——你就发明了这个 Creator Mode。

这个所有的好处都是有代价的。代价是什么呢？实际上我们没有解决的是：虽然我们在 event 这层上做了一个统一的对齐——说你们都要使用同一组 event，然后类型匹配不匹配的，你们就对不起就不行——但是所有的状态管理、插件自己的状态管理还是在自己的。就像刚才我们说的那个 better-sidebar 的插件，它窗口是什么、终端怎么表示，都在自己里面；然后他有的时候当然可以自己创建一个事件推到总线上，让别人可以看到。但是插件和插件之间的语义可能是冲突的。比如说我可以 hook，所以我可以实现一个上下文压缩的插件：每一次上下文输出都压缩 1/2；但如果有两个插件之间可以互相 interfere——比如说我加载了十个自动上下文压缩的插件，每个都压缩到 1/2，那么十次方就是 1/1024，你任何东西输出都被压缩到小到信息就全部丢掉了。也就是说虽然他们之间可以组合，但是比如说他们的先后顺序——一个检查输入、一个改写输入——到底是检查在前还是改写在前，其实我们没有规定。这是个语义，就是和应用语义相关的。Essential complexity 是永远不可能解决的；插件只是说它减少了一些 accidental complexity，以及在你做一些事的时候——比如说我要做这种动态的 UI 生成的时候——它变得更开心了。这是做到的。但是系统里面这些带有冲突的语义——比如说两个 Hook，一个要求停止、另一个要求继续——其实是冲突的；但当你 Hook 运行到停止的时候，这个就被停掉了。这种语义的冲突是永远没有办法在这种架构里解决的。你可能需要另外一个机制，比如说再放一个白板 blackboard，在需要的时候他们再去共享这个状态——那这个时候抽象就有限，当你有这种需求的时候抽象就有泄露。所以插件不是万能的，架构也不是万能的；但是你也可以看到，一个好的架构会给我们带来一些很有趣的启发。

而真正的我觉得，真正的架构给我们带来的是什么呢？带来的是一整个软件的生态。所以说我们前面一直讲了一个简化的模型：我们做一个需求，需求确定了以后就把这个产品 release 出去，release 出去以后他就挣钱了。但是 DeepSeek Harness 走了一个不太一样的路线：他在 release 的时候 release 了一个 nothing——或者说他有一些基本的东西、基础的抽象和一些第一方的东西——他把剩下的东西交给了开源的生态。所以你看到我们上周在北京有一个 OMMYDACH 的活动，这完全是由开发者自己组织的，跟官方没有任何关系，没有任何 DeepSeek 的人到场；我也正是因为我去了、顺便要去北京，所以我顺便到会场闪现了一下。而接口简单、复杂性低、随便 vibe，就意味着它在 DeepSeek Harness 基础上可以长出一整个生态——你想要什么就要什么。所以我自己对这个开源社区的感觉是：开发者被带歪了。如果是我在第一方、就是我在第一方 DeepSeek 发 Harness 的时候，我可能不会 vibe 这些就是这么好的东西——我不会用它来 vibe 一个什么高达驾驶舱——我显然会 vibe 一些更了不起的东西。

所以在我看来，这样的一个 event bus 真正的能力在哪里呢？它不在于接这种 fancy 的小东西——我可以 hook 这个事件，然后把我的 UI 做一个增强——而是——这是一个生态：它当然可以互相增强，比如说调用工具，就有很多工具可以进来，工具还可以互相组合。我第一个想要接入的是 Super App。Super App 只需要一个非常小的抽象层——但是我对 Super App 可能是要改造的：它首先要有一个 Web UI，但没有 Web UI 也行，我可以用一个 bridge 把它和 DeepSeek Harness 连起来。这个 Super App 我只需要支持两个操作——其实是三个：第一个，Super App 里面总是有对象的，比如说打个比方 WPS，我现在在做一个幻灯片，那我第一个操作是我可以把一些对象锁住——比如说第一页、第二页你就别编辑了，我现在锁住；第二个，我可以把这个对象 hand off，从总线上面送到这个模型的上下文里；第三个，我可以把修改的对象从模型的上下文里面拿回来，替换回我的这个 Super App 里。我只需要对 WPS Office 做一个这样最小的改造，我就给一个超级应用赋予了 AI 原生的能力，而且他可以享受到这个 DeepSeek Harness 插件生态里面所有东西的好处。这是一个非常恐怖的能力：DSH 是一个非常小、非常薄、什么也没有的内核层，但是它底下有一整个大的插件生态——这是大模型 AI 的生态；同时我的任何一个 Super App 都可以做到这一点。我今天花 5 分钟的时间 vibe 了一个——当然没有 vibe WPS——我做了这样的一个东西，但是这个 demo 就可以告诉你：任何的 Super App 在这个上面都是可以的。大家用过这个 Excalidraw 吗？你可以用它来拖东西，拖各种东西……OK，这是一个——你就想想这就是一个 Super App、WPS，任何能嵌在网页里的都可以。我可以做一个 bridge，我可以干一件什么事呢？我说 AI 可以制定一下这个 turtle：在框里画一个 turtle 用的元素，有一些文本标签。在这个时候 AI 就开始工作了——所有的编辑你看都是可以照常进行的，但这个对象被锁住了。所以我说我的接口只要对于这个 Super App，我只需要把一些对象给锁住，以及把锁住的对象 hand off 给这个模型，模型再回来。注意：因为我是放到这个总线上的，整个生态都归我。然后——唉有了——一个没有任何 AI 能力的 application，它可以以任何方式把他的任何对象以最合适的形式接入 AI。这是什么呢？你就想想 WPS：你们有没有用过这种什么 Kimi、WorkBuddy，你让他做一个 PPT，然后做了 PPT 以后他自己那个产品团队自己做一个 PPT 的 editor，然后你可以拖那个框，还可以加 comment、加一个注释不满意再让他改。但是你为什么不反过来做这件事——就是这是一个生态，你直接把它摁进去就完了，真正的 AI Native 的东西。你第一方——你看所有东西都可以编辑它，它是 Excalidraw——这个你不满意你还可以再改；你不满意这个龟壳，你还可以把它删掉。做得不错，这是 DeepSeek 的 Flash 版本。这是一个，然后你的空间就大了：你可以做一个 Blender 的 bridge——这就是我们为什么 MCP 呢——只要做一个非常小的 protocol，然后这个 protocol 甚至可以成为 DeepSeek Harness 的一个原生的插件，专门做这个对象的 bridge。然后你甚至可以切换到那个聊天——当然我这个做的，因为我就花了 5 分钟来 vibe 它，做的比较简单，就是一个这样的 AI 聊天框——完全可以把它和这个 bridge 起来。我可以回到这里来编辑它：这个画 turtle 的 Session 还在，然后这个高达驾驶舱依然还能生效。这是第一个：大型 App 的 AI 增强。

然后第二个方向：因为我们的 event bus 的特性，我们可以随便 hook，所以其实我们可以建立一个 Session 和一个模型的双向通道。我们只要允许模型输出一个 HTML 加 JS 的卡片，我就可以把这个卡片放到界面的任何 slot 上。然后这个能力在哪里呢？这个能力在：我可以生成一个卡片，注意这个卡片是有 JS 的——JS 意味着我这里可以放一个按钮、可以放一个输入框、可以放任何东西，我甚至可以放一个 Excalidraw、放一个 WPS；理论上说我可以写一个 React component，就是一个非常复杂的东西就放在这。然后放在这以后，我允许某一些 JS 调用往这个 event bus 上面注入一个事件，我就可以把东西注入到模型的上下文里。我可以把一个动态的 UI 生成出来，并且我可以把 UI 里面的点击、鼠标的点击事件以及里面的状态，通过一段 JavaScript 重新注回上下文里；然后这个上下文完了以后，他可以再指导这个 UI 的更新。这不就是一个 Generative UI（GenUI）的应用吗？所以这我也做了——虽然这也是 5 分钟，怪不得——所以里面还有很多的细节。我只要和他做好一组约定：比如说我只要约定这个 div——一个叫 `dsh-genui` 的一个 div——只要碰到这样的 div 在输出里，我完全是许愿式的就跟插件说我要做这个事；然后他碰到这个，就会把它以一个卡片的方式来……等我稍微缩小一点就能看到全部了。然后它会生成一段带 JavaScript 的代码。当然我现在因为所有代码一次都是重新生成的，所以长度会比较长；但是你总是可以设计 DSH、设计一个好的方式去复用已有的东西，这样你就可以把它做得很短。比如说我现在可以跟 AI 玩成语接龙——以「惊弓之鸟」开局。你可以看他模型的对话过程就是：我这就是相当于我点击了这个按钮以后，这个 JavaScript 会往模型的上下文里面注入这样一个一句话——这个就是字符串拼接的，只要是可以代码做的——然后模型就会开始输出嘛。它接「鸟语花香」；接完以后它可以生成一个对界面的 patch——虽然我现在生成不是 patch，我就直接再生成一个新的卡片。好，有些 bug 不要紧，因为我关闭了思考。这个状态是带着的，带着「鸟语花香」……诶他还不思考，确实还是有些问题。就是完全完全 vibe。然后如果你想要 vibe 任何东西吧——就做一个五子棋，然后要求五子棋的状态在 UI 里，但是所有下棋落子都是模型思考以后做的。对吧，我如果为了让它快……「鸟语花香」「香火不绝」「绝处逢生」……那我再来一个。然后我可以配合它的好处是什么呢？我可以配合一系列的和 dynamic UI 相关的插件：比如说怎么样做上下文的压缩、怎么样做上下文的管理，可能甚至有上下文的 fork；然后以及这个插件生态，一方面是可以更好地让我能和这个 UI 交互，省下上下文；还有以及我甚至可以把整个这个 Session——不要这个聊天框就可以不要了——聊天框就不要了，我可以面对我的一个任务，生成一个真正好的 Generative UI。来我们来看看——嗯对啊，这次他可以这个了，虽然有点 bug，就五子棋是下在线上来了，但我们试一下。对，他开了 thinking——这肯定不是一个成熟的产品；但是你们想回想一下，到这个 ChatGPT 的时刻、GPT-3.5 的时候，我记得我就算是让他输出一个——把从 50 数到 100——他都五十一、五十一、五十一……然后你肯定会觉得这个东西又慢又不好用。但是当你看到一种可能性的时候，他能做到一点的时候，就意味着一定有办法可以做得非常非常好。所以这就是架构。来看一下：你看他在这里下了一个……所以到这里就在 Creator Mode 下，完全这个东西能做出什么，完全取决于你的想象力——你就是在许愿式地来做这件事。

诶，上下文注入——给模型的上下文注入——这个有意思啊。因为动态 UI 我做了这 vibe 的这个插件以后，我需要给每一个 Session 注入提示词：因为你看我的这个插件使用是有条件的，我需要它生成一个带特别标记的 div——相当于我是一个 DSL，你也可以理解成我可以做一个 DSL，然后这个 DSL 可以生成一个 div；然后我必须要模型要知道生成这样的 div 才能变出一个正确的动态 UI 的插件。所以我首先要给模型注入上下文。你看这就是 Cordis 整个生态设计的——不是 Cordis 了，就加上 DeepSeek Harness 的核心层设计的——它只要一个 `ctx.systemPrompt` 的一个事件：你看在这里插入一段 1.5KB 的协议说明，它会勾住这个 event。然后这是插件唯一写进主动模型、写进主动模型的上下文的。然后模型的输出到 UI 状态：提取不新增消息的类型，靠标记加投影——Event Sourcing——对吧，完全是事实，就是我可以根据我的事实的历史来读到：这个里面是不是有——我插件可以检查——同样是 event，就当一个模型的输出结束以后，我可以知道里面有没有，然后有的话它就可以改变我自己的状态，比如说 UI。我可以——我不知道它是怎么实现的——它可以是在往一个 slot 里面去插入这个界面，或者 whatsoever；但这显然也不会入侵到整个系统实现的部分。它有一些 Cordis 服务的依赖，然后一些 session projection 的回调、system prompt。哦他这个有点入侵对吧——他加了一些自己的 library、浏览器 remote session、prompt 打包 profile。然后完全没有动底层的架构，就只靠这个系统的架构来的。
